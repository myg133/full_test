# 验收标准：REQ-011 —— R2 回归轮 `regression-plan` skill + 套件层组合门

> 判据集：**28 条**（AC-001~AC-028），**自包含**于本文件。
> 被验对象：`<package>/skills/regression-plan/`（skill 本体） + `<package>/bin/`（套件层组合门）。
> 判据形式统一为「**可证伪 + 查绝对事实**」：每条都要能指出"改坏什么 → 本条判红"。
> **不可判定时不判通过** —— 找不到被护对象、读不到输入、依赖缺失，一律判红，不许自我豁免。

## 0. 被验对象与命令行契约

**skill 目录**（记作 `$RP`）：`<package>/skills/regression-plan/`

| 路径 | 作用 |
|---|---|
| `$RP/SKILL.md` | skill 入口（frontmatter 含 `name` / `description`） |
| `$RP/references/regression-plan-schema.md` | `regression-plan.json` 的字段契约 |
| `$RP/references/impact-rules.md` | 影响面判定规则（F3） |
| `$RP/scripts/plan-regression.mjs` | 主脚本：产计划 |
| `$RP/scripts/check-plan.mjs` | 校验器：查计划自洽性 |
| `$RP/scripts/lib/*.mjs` | 内部模块（路径可自由，判据不依赖内部命名） |

**CLI 契约**（判据按此调用；实现可加参数，但**不得删改**以下语义）：

```console
node scripts/plan-regression.mjs --changelog <file> --cases <file> --cycle-dir <dir> \
     [--dimensions <file>] [--methods <file>] [--json]
#   → 在 <dir> 内写 regression-plan.json；退出码 0 = 成功 / 1 = 输入或引用非法 / 2 = 用法错误

node scripts/check-plan.mjs --plan <file> --cases <file> --changelog <file> \
     [--dimensions <file>] [--methods <file>] [--json]
#   → 退出码 0 = 计划自洽 / 1 = 查出问题 / 2 = 用法错误
```

**输入样例（判据用的最小夹具）**：
- 用例集 `cases.json`：schema v2，含 **3 个需求条目**（`R-1` / `R-2` / `R-3`）、**7 条用例**，维度取自 `dimensions.json`，方法取自 `methods.json`
- changelog：**6 个变更条目**（编号 `C-1` … `C-6`，按二级及以下标题切分后依次编号），各条用途如下：
  1. `C-1` 带 `@R-1` —— **需求条目命中**（AC-006）
  2. `C-2` 带 `@dim:security` —— **维度显式命中**（AC-007 显式路径）
  3. `C-3` 正文逐字含 `observability` 的 `applies_when` 信号词 —— **维度隐式（信号词）命中**（AC-007 信号路径）
  4. `C-4` 带 `@TC-004` —— **用例显式命中**（AC-008）
  5. `C-5` 带 `@R-2` **且**正文逐字含某方法 `not_applies_when` 短语 —— **方法不适用 → `needs_review`**（AC-017）
  6. `C-6` **无显式引用、正文也未命中任何维度/方法信号** —— **判不了**（AC-012/013）
- ⚠️ **夹具的「角色分离」是硬要求**（干跑实测，否则判据会互斥或变异会逃逸）：
  1. **被方法挡住的用例**（其方法命中某变更条目的 `not_applies_when`）**不得**同时是「需求命中」用例 —— 否则 AC-006（要求它在 `selected`）与 AC-017③ / AC-018（要求它不在 `selected`）**互斥**；
  2. **信号词路径命中的维度必须与显式 `@dim:` 的维度不同** —— 否则 AC-007 的探针「只堵显式路径须判红」无法与信号路径**区分**（堵掉显式路径会连带堵掉信号路径，探针就测不出差异）；
  3. **非 `active` 的用例不得恰好就是被方法挡住的那条** —— 否则「忽略 `status`」这个变异**无观测差异**（该用例本来就不在 `selected` 里），会**逃逸**。

**库文件默认值**：未显式传 `--dimensions` / `--methods` 时，必须回落到**同包内**
`../test-case-design/references/{dimensions,methods}.json`（相对 `$RP`）——
即**库的唯一来源是 test-case-design 里的那两份**，不是 regression-plan 自己的副本。

## A 组：交付物形状（AC-001~AC-004）

### AC-001: `regression-plan` skill 存在且结构合法
- **前置条件**: 被验包目录
- **测试步骤**: ① 检查 `skills/regression-plan/` 存在；② 检查 `SKILL.md` 存在且 YAML frontmatter 含 `name: regression-plan` 与非空 `description`；③ 检查 `references/regression-plan-schema.md`、`references/impact-rules.md`、`scripts/plan-regression.mjs`、`scripts/check-plan.mjs` 四个文件存在且非空；④ 检查两个脚本的 shebang 或首行可被 `node` 直接执行
- **预期结果**: 四项全满足；任一缺失 → 判红并点名缺哪个
- **判据形式**: 查**绝对事实**（文件真实存在且非空），不查"文档里说有"
- **「非空 description」的判定口径**（D45 明确化）：取 frontmatter 里 `description:` 的**值**再判空 ——
  - 值为块标量（`|` / `|-` / `>` / `>-`）→ 取其后的缩进块内容，**块为空即判空**；
  - 值为普通标量 → 剥掉首尾引号后判非空（`""` / `''` / 空值一律**判空**）；
  - ⚠️ 不得用"该行有没有非空白字符"这种近似判定（`description: ""` 的第一个引号就会被当成非空）。
- **类型**: 功能

### AC-002: 每个 skill 都声明版本与依赖（`skill-meta.json`）
- **前置条件**: 被验包目录
- **测试步骤**: 对 `skills/` 下**每一个**含 `SKILL.md` 的目录，检查存在 `skill-meta.json`；解析它必须有 `name`（非空且等于目录名）、`version`（形如 `<数字>.<数字>.<数字>`）、`requires`（对象；值为形如 `>=<x.y.z>` 或 `<x.y.z>` 的约束）；并检查 `name` 与该 skill 的 SKILL.md frontmatter `name` 一致
- **预期结果**: 每个 skill 都有合法声明；`test-execute` 的 `requires` **必须**包含 `test-case-design`（它是硬跨 skill 依赖，见 demand.md §1.2）
- **判据形式**: 查绝对事实；探针：删掉某个 skill 的 `skill-meta.json` → 本条判红；把 `test-execute` 的 `requires` 删掉 → 本条判红
- **类型**: 功能

### AC-003: README 的 skill 清单与实际目录一致
- **前置条件**: 被验包目录 + `README.md`
- **测试步骤**: 取 `skills/` 下全部含 `SKILL.md` 的目录名集合 S；取 `README.md` 的 **skill 清单**集合 R（清单 = README 里**列出 skill 的三种形态的并集**：① 表头首格为 `Skill` 的表格的每一行首格；② 正文里 `skills/<name>` 路径形式出现的 `<name>`；③ 安装树代码块里 `skills/` 根之后的条目名）；检查 S == R
- **预期结果**: 两个集合完全相等；README 漏写或多写任一 skill → 判红并点名
- **判据形式**: 查绝对事实（与目录实际内容比对），不查"README 里说了几个"
- **类型**: 可用性
- **说明**（D45 口径明确化）：本条的基准是 **README 的 skill 清单**，不是"README 提到的一切 skill 名"——
  两者在 README 里顺带提到某个目录名时会不一致（例：正文里写了一句 `skills/xxx` 的路径说明），
  判据与门都按**清单**口径执行，报告里的措辞也必须是"README 的 skill 清单集合"。

### AC-004: 新产物不得打破既有目录契约
- **前置条件**: `test-case-design` 的 `scripts/verify-layout.mjs` + 一个合法的 `test-assets/` 项目
- **测试步骤**: ① 造一个满足 REQ-002B 契约的最小项目；② 在其轮次目录 `test-assets/cycles/R2-CHANGELOG-2.3/` 里放一个 `regression-plan.json`；③ 跑 `verify-layout.mjs`；④ 断言退出码为 0 且无 FAIL 级问题；⑤ **错误位置探针**：另造一个同样的项目，把 `regression-plan.json` 放到**错误位置**（`test-assets/` 根），再跑一次 `verify-layout.mjs`，并据其结果给出**明确结论**
- **预期结果**: ④ 全满足（正确位置不破契约）；⑤ 必须给出二选一的明确结论 ——
  - 若校验器**不查**该位置（退出码 0 且无 FAIL）→ 结论「**位置不受约束**」，本条**判绿**（不得要求实现去管它）；
  - 若校验器**查**该位置（退出码非 0 或有 FAIL 级问题）→ 本条**判红**并点名（该位置受约束，而产物必须放在轮次目录内）
- **判据形式**: 查绝对事实（实跑校验器的退出码与 FAIL 计数）；探针：把 `regression-plan.json` 放到错误位置 → 本条按上述二选一给出明确结论（**不得**两种结论都不给）
- **类型**: 兼容性
- **说明**（D45 覆盖补全）：④ 与 ⑤ 是两个**必须分别有结论**的检查 —— ④ 回答"放对位置会不会破契约"，
  ⑤ 回答"放错位置有没有被守住"。此前正文只写了 ⑤ 的探针却没实现，导致探针无结论。

## B 组：选样正确性（AC-005~AC-011）

> 以下各条的公共前置：用 §0 的最小夹具跑 `plan-regression.mjs` 得到一份计划 `P`。
> 夹具必须覆盖：6 条用例分布在 2 个需求条目、至少 2 个维度、至少 2 种方法、至少 1 条 `status != active` 的用例。

### AC-005: 不得凭空造用例
- **前置条件**: 计划 `P` + 输入 `cases.json`
- **测试步骤**: 取 `P.selected` 与 `P.needs_review` 里全部 `case_id`，逐个在输入 `cases.json` 的 `cases[].id` 里找
- **预期结果**: 全部命中；出现输入里不存在的 id → 判红并点名
- **判据形式**: 查绝对事实（输入用例集的实际 id 集合）
- **类型**: 功能

### AC-006: 命中需求条目的用例必须在 `selected`
- **前置条件**: 同上；夹具含一条带 `@R-1` 的变更条目
- **测试步骤**: 取 `P.changes` 里 `requirement_refs` 含 `R-1` 的变更条目 C；对输入里每条 `requirement_refs` 含 `R-1` 且 `status == active` 的用例 u，断言 u 出现在 `P.selected`
  —— ⚠️ **联合读法（干跑实测补）**：「命中需求条目」指的是 `affected(u)`（见 demand.md F3），而 `selected = affected ∧ ¬method_blocked`。
  故本条的对象是「命中需求条目**且未被方法挡住**」的用例；被方法挡住的用例归 AC-017（`needs_review`），**不在本条范围内**
  （若不排除，AC-006 与 AC-017③ / AC-018 就**互斥**，一条用例会被两条判据同时要求相反的结论）
- **预期结果**: 全部出现在 `selected`；漏一条 → 判红并点名漏了哪个
- **判据形式**: 查绝对事实（输入用例集的实际用例）；探针：把实现改成"只选显式引用的用例" → 本条判红
- **类型**: 功能

### AC-007: 命中维度的用例必须在 `selected`（显式与隐式两条路径）
- **前置条件**: 同上；夹具含一条带 `@dim:security` 的变更条目，**以及**一条正文命中**另一个维度**（如 `observability`）的 `applies_when` 信号词的变更条目
  —— ⚠️ **两个维度必须不同**（干跑实测补）：否则「只堵显式路径」的探针无法与信号路径**区分**（堵掉显式路径会连带堵掉同维度的信号路径），探针就测不出差异
- **测试步骤**: ① 对显式 `@dim:` 引用的维度 D，取输入里 `dimension == D` 且 `status == active` 的用例，断言全在 `selected`；② 对信号词命中的维度 D'，同样断言
- **预期结果**: 两条路径都不得漏；任一漏 → 判红并点名是显式路径还是信号路径
- **判据形式**: 查绝对事实；探针：去掉隐式信号路径的实现 → 本条判红（**只堵显式路径的实现在此判红**）
- **类型**: 功能

### AC-008: 显式引用用例的变更条目必须把该用例选进来
- **前置条件**: 夹具含一条带 `@TC-00x` 的变更条目
- **测试步骤**: 取 `P.changes` 里 `case_refs` 含该 id 的变更条目 C；断言该用例出现在 `P.selected`（或其 `status != active` → 已在 AC-016 处理）
- **预期结果**: 必须出现；否则判红
- **判据形式**: 查绝对事实；探针：实现忽略 `case_refs` → 本条判红
- **类型**: 功能

### AC-009: 不在影响面内的用例不得进 `selected`
- **前置条件**: 同上；夹具含至少 1 条与任何变更条目都无关联的用例
- **测试步骤**: 独立重算影响面：对每条用例 u，判定 `affected(u)` =（其 `requirement_refs` 命中任一变更条目的 `requirement_refs`）∨（其 id 被任一变更条目 `case_refs` 引用）∨（其 `dimension` 命中任一变更条目的受影响维度集）；取不满足 `affected` 的用例集合 X；断言 X 与 `P.selected` 的 `case_id` 集合**无交集**
- **预期结果**: 无交集；有交集 → 判红并点名是哪条用例被多选了
- **判据形式**: 查绝对事实（由输入独立重算）；探针：实现把全部用例都选进来 → 本条判红
- **类型**: 功能

### AC-010: `selected` 必须等于「按计划自记的 basis 重算的并集」
- **前置条件**: 计划 `P` + 输入 `cases.json` + 维度库 + 方法库
- **测试步骤**: 以 `P.changes` 里**记录的** `requirement_refs` / `case_refs` / 受影响维度集为数据，独立重算 `selected` 集与 `needs_review` 集（判据自带实现，不复用被验代码）；逐个 `case_id` 与 `P.selected` / `P.needs_review` 比对（**集合相等**，不是包含关系）；**并**把 `P.undecidable_changes[]` 的 `change_id` 集合与**同一份独立重算**得到的判不了条目集合比对（**集合相等**，与 AC-012 同一个重算源）
- **预期结果**: 三个集合**逐项相等**；多出或缺少都判红并点名差集
- **判据形式**: 查绝对事实（重算结果 vs 计划内容）；探针：实现的选样口径与判据口径不一致（例如漏算维度信号）→ 本条判红；**凭空多报一个 `undecidable_changes` 条目 → 本条判红**
- **类型**: 功能
- **说明**: 这条是本 REQ 的**核心自洽判据** —— 它把"影响面判定"从"实现说了算"变成"可被独立重算"。
- **D45 覆盖补全**：此前本条只比 `selected` / `needs_review` 两集，`undecidable_changes` **不比** →
  凭空多报一个判不了条目可以全绿通过。判不了集合同样必须与独立重算**逐项相等**。

### AC-011: 每条选样都必须有可解释的来源
- **前置条件**: 计划 `P`
- **测试步骤**: 对 `P.selected` 与 `P.needs_review` 的每一条：① `reason` 非空；② `change_refs` 非空且每项都存在于 `P.changes[].id`；③ `reason` 里的来源标记必须**能被独立对上** —— 即 `reason` 中出现的需求条目 id / 用例 id / 维度名 / 信号词，必须确实是对应变更条目与输入/库里的事实；④ **marker 必须指向该用例自己的命中路径** —— 标记里的需求条目必须**被这条用例引用**，标记里的用例 id 必须**就是这条用例**，标记里的维度必须**就是这条用例的维度**，标记里的方法必须**是这条用例所用的方法**；且该标记对应的变更条目必须在 `change_refs` 里
- **预期结果**: 全部可对上；`reason` 为空、指向不存在的变更、引用了输入里没有的 id、或**指向别的用例的命中路径** → 判红并点名
- **判据形式**: 查绝对事实；探针：把所有 `reason` 清空 → 本条判红；**探针：把某条选样的 reason 换成另一条变更/另一条用例的标记（事实都存在，但不是本用例的路径）→ 本条判红**
- **类型**: 可用性
- **说明**（D45 覆盖补全）：此前 ③ 只核对"标记是事实"（实体存在），**不核对它是不是本用例的命中路径** ——
  于是"用一个真实存在、但属于另一条用例的标记"也能过关，说服力为零。④ 把"解释"钉回"这条用例为什么被选中"。

## C 组：诚实性（AC-012~AC-015）

### AC-012: 判不了的变更必须显式列出
- **前置条件**: 夹具含一条**无显式引用、正文也未命中任何维度/方法信号**的变更条目
- **测试步骤**:
  1. 断言该条目出现在 `P.undecidable_changes[]`，且该项的 `change_id` 与 `reason` 非空；
  2. **集合相等**：`P.undecidable_changes[]` 的 `change_id` 集合 == 判据**独立重算**出的判不了条目集合（**不得多报，也不得漏报**）；
  3. **reason 需可核对**：`reason` 非空，且 —— 它引用的需求条目 id / 用例 id / 维度名 / 方法编号必须在**权威来源**（`cases.json` / `dimensions.json` / `methods.json`）里真实存在；并且它必须含**可核对的判不了依据标记**（如"无显式引用""未命中""无信号""判不了""推不出""信息不足"一类说明为什么判不了的措辞）；
  4. **D45 子项（判不了的定义）**：判不了 = **推不出任何用例级影响面**。判据自带一份**独立夹具**（一条只命中**方法短语**、无任何显式引用与维度信号的条目 + 一条**合法引用但无任何用例覆盖**的条目），跑一遍计划，断言这两条**都必须**出现在 `undecidable_changes[]` 且 `summary.impact_complete == false`
- **预期结果**: 四项全满足；任一不满足 → 判红并点名
- **判据形式**: 查绝对事实；探针：实现把这类条目悄悄丢掉 → 本条判红；**探针：实现把"只命中方法短语"或"合法引用但无用例覆盖"的条目静默丢出计划、却仍报 `impact_complete=true` → 本条判红**
- **类型**: 功能
- **说明**: 这是本套件一贯的诚实纪律在 R2 上的落点 —— **判不了就说判不了**（对齐 REQ-006 的 AC-008 / D27）。
- **「判不了」的可操作定义（D45，承接 D36 ①）**：一个变更条目**判不了**，当且仅当它**推不出任何用例级影响面**。形式化：
  - `影响用例(C)` = 满足下列任一条的用例 u：① `C.requirement_refs` 与 `u.requirement_refs` 有交集（需求路径）；② `C.case_refs` 含 `u.id`（用例路径）；③ `u.dimension` ∈ `C` 的受影响维度集（显式 `@dim:` ∪ 正文命中的 `applies_when` 信号词命中的维度）（维度路径）；
  - `全影响面` = 所有变更条目的 `影响用例(C)` 之并；
  - `挡住的用例(C)` = `全影响面` 里那些**用了**被 `C` 的正文命中的 `not_applies_when` 短语所属方法的用例；
  - **`C` 判不了 ⟺ `影响用例(C)` 为空 且 `挡住的用例(C)` 为空**。
  - 推论（两条必须落地的行为）：① **只命中方法短语、且对应不到任何用例**的条目 → 判不了（进 `undecidable_changes` + `impact_complete=false`）；② **合法引用、但无任何用例覆盖**的条目 → 判不了（同上）。
  - **只有**方法短语命中**且确实能对应到具体用例**时，才算"影响面已推得出来"（该用例进 `selected` 或 `needs_review`）。
  - ⚠️ "引用指向的实体**不存在**"不属于本条 —— 那是**坏引用**（输入错误），归 AC-014。

### AC-013: 判不了的变更不得让任何用例进 `selected`
- **前置条件**: 同上
- **测试步骤**: ① 取该判不了条目的正文，按 `P.changes` 记录的维度集与方法集重算：若它本应命中某维度/方法，则该情形必须由实现显式处理；② 断言**不存在**任何一条 `selected` 条目的 `change_refs` 包含该判不了条目的 id；③ **同一约束适用于 `needs_review`** —— 断言**不存在**任何一条 `needs_review` 条目的 `change_refs` 包含该判不了条目的 id
- **预期结果**: `selected` 与 `needs_review` 两边都不得有任何选样条目引用它；一旦出现 → 判红
- **判据形式**: 查绝对事实（计划内容）；探针：实现把判不了条目当成"影响全部用例" → 本条判红；**探针：只把判不了条目挂到 `needs_review` 上（`selected` 干净）→ 本条判红**
- **类型**: 功能
- **说明**（D45 覆盖补全）：此前本条只查 `selected`，**不查 `needs_review`** → 一条只影响 `needs_review` 的条目
  若被多报为判不了（或者反过来，判不了的条目被挂进 `needs_review`），两边都不红 —— 判据出现了一个**双向盲区**。③ 把同一约束补到 `needs_review` 侧。

### AC-014: 坏引用必须报错，不得静默
- **前置条件**: **三份**坏 changelog —— 一条含 `@R-99`（输入里无此需求条目）、一条含 `@TC-999`（输入里无此用例）、一条含 `@dim:not-a-real-dimension`（维度库里无此维度）
- **测试步骤**: 分别跑 `plan-regression.mjs`，断言**退出码为 1**（非 0 非 2），且输出里点名了那个不存在的 id / 维度名
- **预期结果**: 三份都判红（验收侧：被判红 = 实现正确地把坏引用当成错误）；若任一份退出码为 0 或 2 → 判红
- **判据形式**: 查绝对事实（真实退出码）；探针：实现把坏引用静默忽略 → 本条判红
- **类型**: 功能
- **说明**: 静默忽略 = 悄悄漏测，必须报错拦住。
  ⚠️ **三类坏引用是同一类**（D36 ③）：引用指向的实体**在权威来源里不存在** —— 需求条目在 `cases.json` 里、用例在 `cases.json` 里、维度在 `dimensions.json`（**唯一来源**）里。三者都是**输入错误**（该报错），而不是"信息不足"（该标 `undecidable`）——
  判不了的情形是"引用合法但影响面推不出来"（AC-012/013），与本条不是一回事。

### AC-015: 摘要数字与影响面完整声明
- **前置条件**: 计划 `P`
- **测试步骤**: 断言 ① `summary.total_cases` == 输入 `cases.json` 的 `cases[]` 长度；② `summary.selected` == `P.selected` 长度；③ `summary.needs_review` == `P.needs_review` 长度；④ `summary.undecidable_changes` == `P.undecidable_changes` 长度；⑤ 当 `P.undecidable_changes` 非空时 `summary.impact_complete` 必须为 `false`；当其为空时必须为 `true`；⑥ `P.undecidable_changes` 的**条目集合**还必须等于独立重算出的判不了集合（与 AC-010 ② / AC-012 ② 同一个重算源 —— 摘要数字对、但集合本身多报/漏报，同样判红）
- **预期结果**: 六项全满足；任一不符 → 判红并点名哪一项
- **判据形式**: 查绝对事实（计划内容自比 + 与输入比）；探针：把 `summary.selected` 改成别的数 → 本条判红；**探针：把 `summary.undecidable_changes` 改成 0（而数组里有一条）→ 本条判红**
- **类型**: 功能

### AC-020: 同一输入两次跑，输出必须逐字相同（除时间戳）
- **前置条件**: 同一份 changelog + 同一份 `cases.json`
- **测试步骤**: 跑两次到**两个不同的临时目录**；把两份 `regression-plan.json` 逐层比对，**只允许"形似时间戳"的差异**被豁免

## G 组：变异体（AC-025）

### AC-025: 选样核心逻辑必须被变异体测出差异
- **前置条件**: 被验 skill 目录的**副本**（绝不在原地改被验对象）
- **测试步骤**: 在副本上依次注入下列**结构合法**的变异，每个变异都必须让**至少一条**判据判红；变异后还原必须回到基线（基线 = 全绿）
  1. 选样时忽略 `case_refs`（只按需求/维度选）
  2. 选样时忽略维度信号命中（只按显式 `@dim:` 与需求选）
  3. 选样时不做 `not_applies_when` 检查（永远不产生 `needs_review`）
  4. 选样时忽略 `status`（`deprecated` 的用例也选进来）
  5. 判不了的变更条目被悄悄丢弃（不进 `undecidable_changes`）
  6. 坏引用（`@R-99`）被静默忽略（不报错）
  7. `summary.selected` 写成固定值（不随明细变）
  8. `selected` 里塞进输入里不存在的用例 id
- **预期结果**: 8 个变异**全部有效且全部被判出**（"至少一条判据判红"）→ 判绿；**任一变异逃逸**（注入了、行为也变了，却全绿）→ 判红并点名是哪个变异
- **三种结果必须分开（D45 口径订正，不得混为一谈）**：
  | 结果 | 判定依据 | 处置 |
  |---|---|---|
  | **逃逸** | 变异**注入成功**（副本指纹变化 + 语法合法 + 变异后计划与基线**不同**）但**没有任何判据变红** | **判红**并点名 |
  | **无效变异** | 变异**注入失败**（锚点都不可达 / 语法不合法 / 注入后**行为等价**，即变异后的计划与基线逐字相同） | **不计入分母**，**不得**因此判红 |
  | **有效变异不足** | 有效变异数 < 8 | 报「**不可判定**（有效变异仅 N/8）」—— **不得判红**，**也不得判绿凑数** |
- **锚点要求（D45）**：每个变异必须提供**多个备选锚点**（主锚点不可达时依次尝试）；
  锚点注入后必须**自证改动已生效**：① 副本内目标文件指纹变化；② 语法自检通过；③ 变异后的计划与基线**不同**（行为确有差异）。
  ⚠️ 锚点要覆盖**等价写法**（例：实现把 `obj.status` 写成 `obj['status']` 时，锚点不得因字面量不匹配而失效）。
- **判据形式**: 查绝对事实（真实跑出来的判红键）；探针：把实现里某条分支改成恒真 → 本条判红
- **类型**: 功能
- **说明**: 变异必须是**结构合法**的改动 —— 语法错误/崩溃导致的判红是**假检出**，不计入。
- **说明**（D45 的必要性）：此前本条把「变异体注入失效」直接等同于「逃逸」→ 判红 ——
  ① 一个把 `.status` 写成 `['status']` 的**等价**实现会因为锚点不可达而被判红（测的是"正则可达性"，不是"行为差异"）；
  ② 一个**比交付实现更严谨**的实现（组装前过滤掉不存在的用例 id）会让第 8 个变异体被架空 → 被判红。
  两者的正确结论都是「**该变异体无效**」，而不是「实现有漏洞」。
