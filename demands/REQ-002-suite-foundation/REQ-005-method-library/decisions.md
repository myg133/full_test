| D1 | 2026-11-11 | **方法使用从"声明"变成"可核验的事实"** —— `methods_applied[]` 是字符串列表，改一下就能声称用了方法。本 REQ 让"用了 M0.2"必须能在**用例集本身**里找到对应产出 | 字段层面已经脚本化（REQ-002A），但**语义层面**的方法使用还没脚本化：把 `["M0.1"]` 改成 `["M0.1","M0.2"]` 不需要任何真实产出。这是"字段齐备"的更深一层漏洞 | 否 | AC-003/004/003b |
| D2 | 2026-11-11 | 核验失败时区分 **ERROR / WARN / 无法判定** 三者，**不得混同**。ERROR = 产出确实缺失（可机械判定的事实）→ 退出码 1；WARN = 适用性存疑（主观判断）→ 退出码 0 但必须列出；**无法判定 = 单独一类**，既不算通过也不算失败 | "判不了"若被当成"通过"，就是本套件要消灭的虚报通过 —— 宁可漏报通过，不可虚报通过 | 否 | AC-008/013 |

| D6 | 2026-11-11 | **`distinct_expected` 是 `min_cases_by_dimension` 的子字段**（`{"kind":"min_cases_by_dimension","dimension":"boundary","min":3,"distinct_expected":true}`），**不是独立的 kind** | 本 REQ 起草时存在**契约自身的歧义**：F2 的示例 JSON 把它写成子字段，而 F2 的谓词种类表把它列成独立 kind（"上述用例的 `steps[].expected` 至少有 `n` 个不同取值"）。两种写法都能讲通 → 实现方与验收方会各选一种，契约与实现分叉。**以子字段形式为准**：① 示例 JSON 是更具体的规范；②"上述用例"这个措辞只有子字段形式讲得通（独立 kind 得自己再带一遍 dimension） | 是 | AC-003b + `methods.json` M0.2 |
| D7 | 2026-11-11 | **维度跳过也用 `skipped[].method` 记**，形式 `{"method":"dimension:<维度名>","reason":"<非空>"}` —— `skipped[]` 的元素结构**仍以 REQ-002A 为准**（只有 `method` + `reason` 两个字段），不新增 `dimension` 字段 | 需求 F4 说"跳过某维度必须在 skipped[] 里带 reason"，但 REQ-002A 定义 `skipped[]` 每项含 `method` + `reason`（跳过的**方法**）。两处契约不一致 → 实现方只能两边都兼容（Dev 就这么做），但**契约不唯一**。若按 F4 原样写 `{"dimension":"concurrency"}`，`validate-cases.mjs` 会报 `skipped[0].method 必须是非空字符串` → **维度跳过端到端不可交付**。用 `dimension:` 前缀复用既有结构：既不改上游契约，又让维度跳过真能交付 | 是 | AC-006 |
| D8 | 2026-11-11 | **方法编号分两段**：`M0.x` / `M4.x` = 架构稿 Layer 0 的**必选测试点**（测什么：正常路径/边界值/异常输入/非法迁移/幂等/服务端校验/数据质量）；**`M1.x` = 本 REQ 的测试设计方法**（怎么测：等价类/边界值分析/判定表/状态迁移/正交/场景法）。`methods.json` 只收录 `M1.x` | 架构稿的 `M0.x` 与 REQ-005 起草时定义的 `M0.x` **同号不同义**：架构稿 M0.5=幂等、方法库 M0.5=正交；架构稿 M0.1=正常路径、方法库 M0.1=等价类。而 REQ-002A 的 `case-schema.md`（**已交付**）里 `method: ["M0.1","M4.5"]` 用的就是架构稿那套语义 —— 同一个 `methods_applied` 字段会承载两套含义，核验结果必然错乱。编号段分离后：既不改已交付契约的语义，又让两套编号不再打架。编号格式仍满足 REQ-002A 的 `/^M\\d+\\.\\d+$/`（所以不能用 `D0.x`）。出现 `M0.x`/`M4.x` 时，`check-methods.mjs` 报**"无法判定"**（该编号不在设计方法库内），**不得默认通过** | 否 | AC-003/004/003b/005 + `methods.json` |
