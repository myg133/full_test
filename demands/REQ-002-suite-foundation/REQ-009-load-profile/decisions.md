## D127　`load-profile` 的入口脚本与产物落位

**决策**：

1. 入口脚本固定为 **`skills/load-profile/scripts/make-load-profile.mjs`**；
   自检器为 **`skills/load-profile/scripts/check-load-profile.mjs`**
   （两个都必须可执行、首行 `#!/usr/bin/env node`、`node --check` 通过）。
2. `--out-dir` 的语义是**目标项目根**（不是「产物目录」）。产物固定落在：

```
<out-dir>/test-assets/load/
├── report.json                                  # 压测计划清单（套件 ↔ 场景映射 + 未决问题）
├── scenarios/<场景>.json                        # 负载模型本体（每个容量目标一个）
└── suites/LOAD-<编号>-<短名>/
    ├── scenario.json                             # 套件级**引用件**
    └── suite.json                                # scope=load / executor=load / cases_file=scenario.json
```

3. 工具**只写** `<out-dir>/test-assets/load/`，该路径之外的任何位置一律**只读**。

**理由**：

- 上游目录契约规定压测资产住在 `test-assets/load/`（架构 §2.2 目录树 / `project-layout.md` §2.5）。
  若 `--out-dir` 指「产物目录」，实现者就得自己拼 `test-assets/load/` —— 拼错了上游校验器
  `listFiles(test-assets)` 递归找 `suite.json` 时**根本扫不到**（等于产物不存在）。
- 把 `--out-dir` 定义成**项目根**，「只写 out-dir」这条红线才有**机械可核**的落点
  （AC-026 的核点 = `<out-dir>` 下除 `test-assets/load/` 外一切逐字未变）。

**影响面**：F1.1 / F8；AC-001 / AC-026；`references/load-scenario-format.md`。

## D130　「不破坏既有目录契约」判到**上游校验器的真实输出**，不判「整体 rc=0」

**决策**：「新产物不得打破既有目录契约」判法为：

1. 把 load 产物放进 §0.4 的最小项目根副本；
2. **实跑**上游 `skills/test-case-design/scripts/verify-layout.mjs <项目根>`；
3. 断言：**该 load 套件的 `suite.json` 路径相关的判定行全是 `[OK]`**，
   且**没有任何以该路径开头的 `[FAIL]` 行**（按相对路径 grep）。

⚠️ **不判**上游对**整个项目根**的 rc=0。

⚠️ **三分支（前置条件分支不许漏）**：

| 情形 | 判定 |
|---|---|
| ① 被引用的**环境文件不存在**（前置条件不满足） | **不可判定**（前置不满足），**不算实现违约**、**不判 FAIL** |
| ② 环境文件存在、上游对该套件报了**其它**问题 | **判 FAIL** |
| ③ 环境文件存在、上游对该套件**全 `[OK]`** | **判 PASS** |

**理由**：

- 上游校验器用 `listFiles(test-assets)` **递归**找所有 `suite.json` ⇒ load 套件**自动**受
  那套强制约束（字段完整 / 枚举合法 / `suite` 名与目录名一致 / `cases_file` 指向的文件存在
  且不越出项目根 / `environment` 同名文件存在）。
- 但上游整体 rc 还额外要求 `environments/_schema.json` 存在、环境 `credentials` 齐全、
  `test-assets/cycles/`（`cycle.json` + `index.json`）、`.gitignore` 忽略 `.test-artifacts/`
  —— **那些不在本 REQ 的写入范围**内 ⇒ 拿整体 rc 当判据 = **永远判红的假判据**。
  （这是需求方实测后订正的口径。）
- ⚠️ 实测：上游对「环境文件缺失」是**单独一行** `[FAIL] ... environment "local" 在
  test-assets/environments/ 中不存在` ⇒ 只按「该路径相关行全 `[OK]`」判，
  会把**前置条件不满足**误判成**实现违约** ⇒ 必须有分支 ①。
  环境文件**不由本 REQ 写**（写入范围只有 `test-assets/load/`）⇒ 缺它时**不可判定**，不判 FAIL。

**影响面**：F6；AC-004 / AC-019。

## D131　压测上下文 JSON 的顶层字段集**封闭 5 个**

**决策**：上下文 JSON 顶层**恰为** `schema_version` / `service` / `environments` / `workloads` /
`open_questions` 五个字段；出现表外字段（如 `load_scenario` / `cases` / 顶层 `thresholds`）⇒
**输入非法 rc=1**。

| 字段 | 必需 | 备注 |
|---|---|---|
| `schema_version` | 是 | 必须 `== 1` |
| `service` | 是 | 封闭 2：`name`（非空）、`description`（可选） |
| `environments` | 是 | ≥1 项；元素封闭 2：`name` / `base_url` |
| `workloads` | 是 | ≥1 项；元素封闭 10（见 D133 / D134） |
| `open_questions` | 否 | 默认 `[]` |

**理由**：

- 「封闭」是**上游同款**做法（`suite.json` 的顶层 9 个、环境配置的顶层 9 个都是封闭集）——
  封闭集才能让「多写一个字段」成为**可判红**的违规，而不是各写各的。
- 顶层**不许**放 `thresholds`：`thresholds` 属于**每条容量目标**（不同目标的阈值不同），
  放顶层会让「哪个目标的阈值」无从判定。
- `environments` 必填：负载模型要指明**打哪个环境**，而环境是**别人**的资产（见 D131 附注）。

**附注**：`environments[]` 只是「**目标环境清单**」，实现**不得**创建/修改环境文件
（写入范围只有 `test-assets/load/`）—— 被 workload 引用的环境文件**是否存在**，是 F6 校验层判据的
**前置条件**（D130 / D146 的分支 ①）：不存在 ⇒ **不可判定**，**不算实现违约**。

**影响面**：F1.2；AC-005。

## D132　上下文的引用必须完整（不悬空），且必须**先于产物**拒绝

**决策**：下列三类悬空一律 **rc=1**，且 stderr **点名坏点**，且**不留半份产物**：

1. `workloads[].environment` ∉ `environments[].name`；
2. `workloads[].target` 不合 `^(GET|POST|PUT|DELETE|PATCH|HEAD|OPTIONS) /.*$`；
3. `workloads[].id` / `name` 格式错，或 `id` **重复**。

**理由**：

- 悬空引用会一路飘到产物里（场景的 `environment` 指着一个不存在的环境），到执行侧才炸 ——
  那时错已经写进产物了。**在输入层拒绝**才能保证「不留半份产物」。
- `id` 重复会让「场景 ↔ 容量目标」的一一对应失效（AC-013 的核点）。

**影响面**：F1.3；AC-006 / AC-007。

## D133　workload 条目字段集**封闭 10 个**

**决策**：workload 条目**恰为** `id` / `name` / `target` / `environment` / `profile` /
`thresholds` / `thresholds_source` / `tool` / `args` / `requirement_refs` 十个字段。

- `id`：`^WL-\d{3}$`，文件内唯一；
- `name`：`^[a-z0-9][a-z0-9-]*$`（= 场景短名 = 场景文件名去扩展名）；
- `profile`：封闭 2 —— `type` ∈ `constant`/`ramp-up`/`ramp-down`/`spike`/`soak`，
  `steps[]` 元素封闭 2 —— `duration_s`（整数 ≥1）、`concurrency`（整数 ≥1）；
- `tool`：封闭 2 —— `runner` ∈ `loadtest`/`python`、`runtime` ∈ `bun`/`python`/`node`；
- `args`：开放键值，原样透传；
- `requirement_refs`：string 数组（需求条目引用），缺省 `[]`。

**理由**：

- `profile.type` 的 5 个取值覆盖常用负载画像（恒定 / 爬坡 / 降压 / 尖峰 / 浸泡），
  足够表达「容量目标 → 负载模型」的映射，又不至于多到失去约束力。
- `tool.runtime` 单独列出：`loadtest` 的运行时是 `bun`（架构 §2.3 示例），`python` runner 的运行时是 `python`
  —— runner 与 runtime 是**两件事**（架构 §5.6 只给了 `runner` 的两个取值，runtime 由本 REQ 补齐）。
- `args` **开放**：runner 的参数随工具而变，本 REQ 不绑定工具 ⇒ 不该封闭它；
  但契约要求**逐字透传**（AC-010），保证可追溯。

**影响面**：F1.3 / F1.5 / F1.6；AC-005 / AC-007 / AC-008 / AC-010。

## D134　`thresholds` 与 `thresholds_source` **成对出现**；枚举越界一律 rc=1

**决策**：

| 情形 | 判定 |
|---|---|
| 两个都无 | 合法（没有指标来源）⇒ 产物走 `not_provided` 分支（D137） |
| 两个都有 | 合法（`thresholds_source` 非空；`thresholds` ≥1 键且键 ∈ 白名单） |
| **只给一个** | **输入非法 rc=1** |

`thresholds` 键白名单（封闭 6）：`p50_latency_ms` / `p95_latency_ms` / `p99_latency_ms` /
`error_rate` / `throughput_rps` / `max_concurrency`；延迟/吞吐/并发 = number ≥ 0，
`error_rate` = number ∈ `[0,1]`。**表外键 ⇒ rc=1。**

**理由**：

- 架构 §2.3 L191：「`thresholds_source` 是必填字段 —— 没有指标来源就不该有阈值，
  凭空拍的阈值会让压测结论毫无意义」。**成对规则**把这条从「叮嘱」变成**结构约束**：
  「有阈值没来源」在**输入层**就被拒，不会流到产物。
- 「有来源没阈值」也拒：来源说的是「按 REQ-005 的指标判定」，连阈值都没给，那来源是空的。
- 键白名单封闭：否则 `p95_latency_ms` / `p95_ms` / `latency_p95` 三种写法都能过，
  判据无从核「键名合法」。

**影响面**：F1.4；AC-008 / AC-011 / AC-014。

## D135　负载模型本体的顶层字段集**封闭 14 个**

**决策**：`test-assets/load/scenarios/<场景>.json` 的顶层**恰为** 14 个字段：
`schema_version` / `id` / `name` / `service` / `target` / `environment` / `profile` /
`thresholds` / `thresholds_source` / `thresholds_status` / `tool` / `args` /
`traceability` / `open_questions`（其中 `thresholds` 与 `thresholds_source` 是**条件字段**，见 D137）。

`traceability` 封闭 3：`workload_id` / `requirement_refs` / `case_refs`。

**理由**：

- 上游对 `cases_file` 指向的文件**只校验存在、不校验内容**（实测）⇒ 负载模型的字段集
  **一条上游都不管** ⇒ 这条**必须由本 REQ 的门判**，而门要判「封闭集」就得先有封闭集。
- `traceability` 独立成段而不是散在顶层：负载模型的**身份**（来自哪个容量目标）、
  **需求出处**、**功能用例出处**是三件不同的事，合成一段才能一条判据核全（D150）。
- **顶层不放 `meta`**：产物里不放生成时间戳 ⇒ 幂等就是「两份产物逐字相同」（D151），
  不用排除任何字段。

**影响面**：F2.1 / F2.2；AC-009。

## D136　梯度与阈值必须**逐字可追溯**到输入

**决策**：场景本体里的 `profile` / `thresholds` / `thresholds_source` / `tool` / `args` /
`target` / `environment` / `service` 必须**逐字等于**输入上下文对应值（键序无关，值逐字）；
`profile.steps[]` 的**顺序**也必须一致。

**理由**：

- 「可追溯」的最低要求是「能在产物里看到原始值」，而不是「实现者照着抄了一遍大概」。
  逐字相等 ⇒ 门能做集合/字面比对 ⇒ 「凭空把并发从 10 改成 50」这类**漂移**当场判红。
- 步序也要一致：负载画像的**先后**（先 10 并发爬到 20）本身就是语义。

**影响面**：F2.1；AC-010。

## D137　「没有指标来源」的表达 = `thresholds_status` 二态 + **键的有无**

**决策**：

| `thresholds_status` | 必须满足 |
|---|---|
| `provided` | `thresholds` 与 `thresholds_source` **两个键都存在**且逐字等于输入；`open_questions` 里**不得**有 `topic == "thresholds"` 的条目 |
| `not_provided` | **不得**存在 `thresholds` 键、**不得**存在 `thresholds_source` 键；`open_questions` 里**必须**有 ≥1 条 `topic == "thresholds"` |

**理由**：

- 单靠「不写 `thresholds` 键」不够：读者分不清「没阈值」是**故意**还是**漏了**。
  `thresholds_status` 把「故意没阈值」显式写出来。
- 「不得写无来源的阈值」用**键的有无**表达 ⇒ **结构性**保证，不是口头承诺（可机械核）。
- `not_provided` 必须配一条未决问题 ⇒ 「缺什么、谁来补」有出处（架构 §3.4 的跳过示例同款思路：
  `{ "scope": "load", "reason": "需求未给任何性能指标，无阈值可依" }`）。

**影响面**：F2.3 / F5；AC-011 / AC-014 / AC-021。

## D142　`suite.json` 用上游的 9 字段封闭集；`scope`/`executor` 必须是 `load`（**配对由门判**）

**决策**：

1. `suite.json` 顶层 ⊆ 上游 9 个允许字段
   （`suite` / `requirement` / `scope` / `environment` / `cases_file` / `executor` /
   `base_url_from` / `tags` / `report`）；**出现表外字段（含 `load_scenario`）⇒ 违规**
   （上游 `verify-layout.mjs` 对 `suite.json` 的顶层字段集**封闭**，**上游会拦**）。
2. 六个必填（`suite` / `requirement` / `scope` / `environment` / `cases_file` / `executor`）
   都在且非空；`suite` == 所在目录名；`cases_file` == `scenario.json`。
3. `scope == "load"` 且 `executor == "load"`。
   ⚠️ 上游**只**校验两者各自的**枚举合法性**，**不强制配对关系**（实测：`executor: "api"`
   的 load 套件上游判 `[OK]`）⇒ **「配对」这条由本 REQ 的门判**。

**理由**：

- 复用上游封闭集 ⇒ 产物天然满足上游约束，不与上游打架。
- `executor` 必须是 `load`：负载模型是**压测**套件，配到 `api` 就是**误配对** ——
  压测套件被当功能用例跑，跑出来的是**假象**。既然上游不拦，这条必须由门拦。
- `cases_file` 指向 `scenario.json`（**不是** `cases.json`）：上游 `loadCases()` 硬要求
  `doc.cases` 是数组 ⇒ 场景文件**不能**做成 cases 形态（架构 §2.3 L77）。

**影响面**：F3.3；AC-016 / AC-020。

## D143　套件级 `scenario.json` 是**引用件**：封闭 3 + 元素封闭 3 + 防漂移快照

**决策**：

| 顶层字段 | 约束 |
|---|---|
| `schema_version` | `== 1` |
| `suite` | **等于**所在目录名 |
| `scenarios` | 数组 ≥1 项；元素封闭 3：`path` / `id` / `name` |

- `path`：相对**套件目录**解析，必须指向**真实存在**的 `scenarios/<name>.json`；
- `id` / `name`：必须**逐字等于**本体文件里的 `id` / `name`。

**取舍说明**（需求方 §7 第 3 点）：引用字段名取 **`scenarios`（数组）**，
**不取** `load_scenario`（单值）。理由：

- `load_scenario` 这个名字**不能**进 `suite.json`（上游封闭集，见 D142），
  但**可以**出现在 `scenario.json` 里；本 REQ 选择**更不用**它 —— `scenarios` 数组自带复数语义，
  与「一个套件可对多个场景」（D144）一致，单值字段会逼实现者在 N>1 时做二选一。
- 元素里带 `id`/`name` 两个**快照**字段：只给 `path` 的话，引用与本体之间没有可比对的锚点，
  「本体改了身份、引用没改」这种漂移**判不出来**。

**理由（架构 §2.2）**：架构 §2.2 的目录树明写套件级 `scenario.json` 是「**指向** `scenarios/`」的
**引用**，本体在 `test-assets/load/scenarios/<场景>.json` ⇒ 引用与本体**必须分开**。

**影响面**：F3.2 / F4.1 / F4.2；AC-017。

## D144　一个套件可对多个场景（**多对一**），按 `environment` 分组

**决策**：同一 `environment` 的所有 workload 归入**同一个**套件；一个场景只属于一个套件。

**理由**：

- 压测套件是「**一次跑一批**」的单位，而「一次跑」的分界自然是**环境**
  （环境不同 ⇒ base_url / 凭证 / 容量都不同，混在一套里没法跑）。
- 反过来「一个 workload 一个套件」会把套件数炸开（4 个 workload ⇒ 4 个套件目录），
  而同环境的负载画像（ramp-up / constant / spike）本来就该**一起跑**。
- 引用件用数组（D143）正是为多场景准备的。

**影响面**：F3.1；AC-015 / AC-017。

## D145　「可被消费」判到**加载层**（`loadSuite()` 真实调用不抛错）

**决策**：「可被消费」的第一层判法 =
**单独进程**调用上游 `skills/test-execute/scripts/lib/suite-loader.mjs` 的 `loadSuite()`
去解析该 load 套件的 `suite.json`，断言**不抛错**（拿真实退出码 / 真实返回值）。

⚠️ **不判**：`run-suite.mjs --dry-run` 跑通（`load` 执行器未实现 ⇒ 必然抛错 ⇒ 假判据）；
⚠️ **不判**：`loadCases()` 能消费 `cases_file`（上游 `loadCases()` 硬要求 `doc.cases` 是数组 ⇒
`scenario.json` 不能做成 cases 形态）。

**理由**：

- 「产品能不能被上游消费」的**唯一**真实答案只能问上游本人 ⇒ 门必须**实跑**上游加载层，
  不许自己解析 JSON 冒充。
- 上游 `loadSuite()` 只校验 `suite.json` 的 6 个必填字段，**不加载 `cases_file`**
  ⇒ 它恰好是「加载层可解析」这个粒度的裁判。

**影响面**：F6；AC-018。

## D146　场景模型 ↔ 套件的**双向覆盖完整性**（AC-019）

**决策**（**逐个字面量/逐个集合各算各的**，不合并、不遮蔽）：

① **每个 workload（容量目标）恰好被一个套件引用**（不悬空、也不被两个套件重复引用）；
② **每个 load 套件至少引用一个场景模型**（不得有空引用件）；
③ **每个场景模型至少被一个套件引用**（**不得有孤儿场景**：生成了却没人引用）；
④ **不得有孤儿套件**（引用了**不存在**的场景模型）；
⑤ 每个套件引用的 id 集合 **恰等于** 该套件 `environment` 下应有的 workload id 集合。

**理由**：

- 与 **AC-013**（「场景模型 ↔ 容量目标」的一一对应）**分工不同**：AC-013 管模型**有没有**，
  本条管模型**落没落到套件里**。两条不重复、不互相遮蔽。
- 与 **AC-017**（「引用件可解析 + 与本体不漂移」）**分工不同**：AC-017 管**引用本身对不对**，
  本条管**引用的覆盖完整不完整**。AC-017 的 ⑦（引用集合 == 应含集合）只是本条 ⑤ 的一半，
  本条额外覆盖「孤儿场景」与「孤儿套件」两个方向。
- 本条**天然不许恒真**：删掉一个套件目录、让某个 workload 落空、留一个没人引用的场景、
  引用一个不存在的场景 —— 四种违规都**必须**真红。
- 需求方订正 3 的裁定：AC-004 与 AC-019 原先逐字重复（29 条里实际只覆盖了 28 件事），
  故 AC-004 保留「上游对该套件的真实结论（三分支）」，AC-019 换成**不重复**的新判据。

**影响面**：F4.4；AC-019。

**影响面**：F6；AC-019。

## D147　load 套件指向的环境**不得**有 `driver` 字段（**上游不拦，本 REQ 的门判**）

**决策**：压测套件所指向的环境配置**不得**出现 `driver` 字段。

⚠️ **措辞纪律**：上游**只**校验 `driver` 的**枚举合法性**
（`driver: "load"` 被上游判 `[FAIL]`；而 `driver: "api"` 是**合法枚举** ⇒ 上游**放行**）
⇒ 「压测套件的环境不该有 `driver`」这条**上游管不住**，**由本 REQ 的门判**。

**理由**：

- 上游 `resolveDriverName()` 的优先级是「**环境 `driver`** → `suite.json.executor`」
  ⇒ 环境一旦写了 `driver: "api"`，`executor=load` 就被**覆盖成 `api`**
  ⇒ 压测套件被当功能用例跑 ⇒ 跑出来的是**假象**（「能跑通」但跑的不是压测）。
- 环境的 `driver` 枚举只有 `api` / `mock` ⇒ **任何**合法取值都会覆盖掉 `executor=load`
  ⇒ 结论：「load 套件的环境**不得**写 `driver`」，不是「不要写 `driver: "load"`」。

**影响面**：F6 / F3.3；AC-020。

## D148　`executor` 必须是 `load`；压测套件**不得**产出 `cases.json`

**决策**：

1. 每个 load 套件的 `suite.json` 的 `executor` **必须是 `load`**（上游**只**校枚举、不校配对 ⇒ 门判）；
2. load 套件目录**不得**出现 `cases.json`；
3. 负载模型本体**不得**是「步骤 → 预期」形态（场景字段集封闭 14 个，天然不含 `steps` / `expected`）。

**理由**：

- 同 D142：`executor: "api"` 上游放行 ⇒ 误配对 ⇒ 门判。
- 架构 §2.3 L77 明写：压测用例**不是**「步骤 → 预期」形态，硬套进 `cases.json` 会让它变形
  ⇒ 压测套件**不写** `cases.json`（REQ-006 的用例设计侧才写）。

**影响面**：F3.3 / F4.3；AC-016 / AC-020 / AC-024。

## D149　未决问题条目封闭 3 字段（`id` / `topic` / `question`）

**决策**：未决问题条目**恰为** 3 个字段：`id`（`^OQ-\d{3}$`，文件内唯一）、
`topic`（∈ `thresholds` / `coverage` / `runner` / `other`）、`question`（非空 string）。

**必须留痕的两种情形**：
① `thresholds_status == "not_provided"` ⇒ ≥1 条 `topic == "thresholds"`；
② `case_refs` 为空（该负载目标在功能用例集里无对应用例）⇒ ≥1 条 `topic == "coverage"`。

**理由**：

- `topic` 取值**封闭**是关键：不封闭就没法判「该留的那类留了没有」——
  只判「数组非空」的话，实现塞一条 `topic: "other"` 就蒙混过关。
- `id` 唯一 ⇒ 未决问题能被**点名引用**（将来执行侧要回来看某条未决问题时用得上）。
- 只列 4 个 topic：够用且封闭；再细分就会逼实现在「分类」上做无意义的争论。

**影响面**：F2.4 / F5；AC-021 / AC-023。

## D150　与功能用例集只做**链路存在性**对账（不派生用例）

**决策**：对账规则（机械可算）：

1. 取输入用例集 `cases[].steps[].action`；
2. **归一化**：取「方法 + 空格 + 路径」，并**删掉路径中所有 `{...}` 占位符段**
   （`GET /api/v1/orders/{id}` → `GET /api/v1/orders`）；
3. 归一化结果**等于** workload 的 `target` 的用例 id，按用例出现顺序去重 ⇒ `case_refs`；
4. `case_refs` 必须**恰等**该集合；
5. `case_refs` 为空 ⇒ 必须留 `topic == "coverage"` 的未决问题。

**明确不做**：不派生任何用例、不写 `cases.json`、不改功能用例集。

**理由**：

- 需求方 §7 第 6 点的倾向：**要，但只做「链路存在性」对账**。价值在于
  「这条被压的链路，功能用例集里到底有没有对应用例」—— 没有 ⇒ 压测结论**没有回归护栏**，
  这个事实必须显式，而不是靠人记得。
- 归一化（去 `{}` 占位符）是必要的：功能用例的 action 天然带路径参数
  （`GET /api/v1/orders/{id}`），而负载目标不带（`GET /api/v1/orders`）。
  不归一化就永远配不上，对账就成了摆设。
- 「恰等」而非「包含」：多出来的 `case_refs` 说明实现**自己捏**了对应用例。

**影响面**：F4.3；AC-024。

**理由**：

## D152　只写 `test-assets/load/`，`environments/` / `cycles/` / 输入一律只读

## 门侧技术纪律（**不占决策号**；对应施工单 §5 的 10 条要求 + 需求方订正 5 条）

1. **sha 钉版**：脚本自算 sha256 与 `QA009_SCRIPT_SHA` 比对；不符 ⇒ `0 PASS / 1 FAIL` 退出。
2. **三态**：`PASS` / `FAIL` / **不可判定**（不可判定 ≠ 通过，退出码一律非 0）。
3. **条数动态取**：判据条数取 `acceptance.md` 的 `### AC-` **实际条数**；
   决策号取 `decisions.md` 的 `^## D[0-9]+` **实际集合**（按**数值**排序，不写死）。
4. **失败键口径**：判定失败时输出**必须**以 `FAIL <AC-xxx>` 开头的一行 ⇒ 外部探针取 `^FAIL` 行做差集。
5. **检测口径 = 新增失败键**（变异运行的失败键 **减去** 基线失败键），**不用对称差**。
   ⚠️ **基线失败键只取 `^FAIL` 行** —— `PASS` / `UNDEC` 行里也有 AC 编号，混进来会让基线键集合
   变成**全集** ⇒ 此后任何变异的「新增失败键」都恒等于全集 ⇒ 整套检测沦为橡皮章。
6. **只读被验包**：一切变异在**副本**上做。
7. **变异体套件**：≥6 个有效正控（**每个判据族至少 1 个**）+ ≥1 个**负控 M0**
   （打不到任何判据的无害篡改，必须**未检出**）。注入方式 = **入口脚本包装（shim）**：
   原实现 move 成 `make-load-profile.real.mjs`，包装层跑完原实现后篡改产物。
   ⚠️ **包装层必须保留原权限位**（`cat >` 新建的文件拿 umask 默认值 644 ⇒ 包装层自身不可执行
   ⇒ AC-001 判红 ⇒ **每个**变异体都被误报）。
   ⚠️ **包装层里的篡改代码必须是 JavaScript**（不是 Python）。
   ⚠️ **篡改未生效时只打标记、不改退出码**（门会用同一入口脚本跑多种形态；某个形态下目标结构不存在 ⇒
   篡改必然不生效；此时非 0 退出码会让门把「合法形态不被接受」判红 ⇒ 污染全部判定）。
8. **退出码**：0 = 全通过；1 = 有 FAIL / 不可判定 / 变异逃逸 / 负控失败 / sha 不符；2 = 用法错误。
9. **可被覆盖的坑**：
   - 复算器**不得 import 被验包的任何模块**（否则等于用被验实现验证被验实现）；
   - 「能不能被上游消费」只能问上游本人（**单独进程**实跑上游加载层 / 校验器，拿**真实退出码**）；
   - 门**不得**写「上游会拦」而上游其实不拦
     （实测：`driver: "api"` 上游放行、`executor: "api"` 上游放行、场景内容上游**一条都不管**、
     套件目录名上游不校 ⇒ 这四条**全部由门判**）；
   - 门**不得**要求执行器能跑（`load` 执行器未实现 ⇒ `--dry-run` 必然抛错）
     ⇒ 落点是**文件系统上的外部证据**（跑完 `<out-dir>` 下不得出现 `runs` / `evidence`），
     **不是**「门源码里没有某个字面量」—— 后者换个写法就能绕过，且不是绝对事实。
10. **环境变量**：`QA009_SCRIPT_SHA`（sha 钉版）/ `REQ009_NO_MUT=1`（跳过变异体套件）/
    `QA009_WORK_ROOT`（工作目录父目录）/ `QA009_KEEP_WORK=1`（保留工作目录）。
11. **上游模块缺失 ⇒ 判【不可判定】，不许判 FAIL**（环境问题 ≠ 实现违约；不可判定 ≠ 通过 ⇒ 退出码仍非 0）。
    落点：**AC-004**（缺上游校验器 `verify-layout.mjs`）与 **AC-018**（缺上游加载层 `suite-loader.mjs`）——
    同一门里对同一类情况**必须给同一种结论**（需求方审门缺陷 5 的裁定）。
12. **不许判上游对整个项目根 rc=0**（那些前置条件不在本 REQ 的写入范围内 ⇒ 永远判红的假判据）；
    环境文件缺失 ⇒ **不可判定**，不算实现违约（这条落在 **AC-004**）。
13. **AC-029 的决策号核对必须「逐个字面量各算各的」**（REQ-007 的 F-01 同类漏洞）：
    ①**每一个范围字面量自身**展开后的集合必须 == 实际决策号集合；
    ②文件里出现的**决策号并集**必须 == 实际决策号集合；
    ③不得出现本 REQ 之外的决策号。
    ⚠️ ①若先把所有字面量并成一个大 set 再比，就退化成 ② ⇒ 等于没加 ① ⇒
    「写 `D127~D153`、同文件别处补一句 `D154`/`D155`」就能逃逸。
