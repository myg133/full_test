## D72　输入合法性**两层划分**（结构层 → 报错；内容层 → `unresolved`）

**背景**：施工单 F1 与 F2 之间存在**直接冲突**：

- F1：`reproduction`（含非空 `command`、非空数组 `steps`、非空 `expected_failure`）是**必填**，
  缺必填 ⇒ **报错退出**；
- F2 规则 3：`reproduction` **缺失**或 `steps`/`expected_failure` 为空 ⇒ 处置 **`unresolved`**（不是错误）；
- F6：「不得把『信息不足』悄悄变成『复用』或『派生』」。

若按 F1 严格执行，`unresolved` 的这条入口**永远走不到**；若按 F2 严格执行，F1 的「必填字段校验」被架空。

**决策**：把输入合法性分成**两层**：

| 层 | 判定对象 | 违反的后果 |
|---|---|---|
| **结构层** | 字段**缺失**、**类型错**、**枚举越界**、`id` 格式错/重复 | **报错退出**（退出码 1）+ stderr 点名 + **不留半份产物** |
| **内容层** | 字段在，但**内容不足以派生**（`reproduction` 整体缺失 / `command` 空 / `steps` 空 / `expected_failure` 空） | **不报错** → 处置 `unresolved` + **非空 `reason`** |

**理由**：

1. 「缺陷单格式非法」与「这条缺陷还没查清」是**两件不同的事**。前者是文件坏了，后者是业务输入还不完整。
2. `unresolved` 的存在意义就是"显式说不知道"。把内容层也做成报错，等于让工具对真实输入闭口不谈 ——
   「显式说不知道」就退化成了「假装输入坏了」，那正是 F6 要防的事。
3. 分层之后，B 组（结构层）与 C 组（内容层）的判据**互不遮蔽**，各自可机械核。

**被否掉的替代方案**：

- ❌ 「`reproduction` 缺失直接报错」—— F2 规则 3 变成死条款；
- ❌ 「全部按内容层处理，结构层也不报错」—— 门禁形同虚设，`defects` 不是数组也照样往下跑。

**影响面**：F1.1~F1.4；判据 AC-005/AC-006/AC-007/AC-008（结构层）与 AC-012（内容层）。

## D73　`case_refs` 部分命中 ⇒ 整条改判 `unresolved`

**背景**：F2 规则 1 说「`case_refs` 非空 → 处置 `reused`」，但同一条规则又说「**必须**能在传入的用例集里找到它们；
**找不到 → 该缺陷改判 `unresolved` 并给理由**」。多条 `case_refs` 时，"部分命中"算什么，规格未说。

**决策**：**全部命中才算 `reused`；任一未命中 ⇒ 整条缺陷改判 `unresolved`**，
`reason` **点名那个找不到的 id**。**不得部分复用**。

**理由**：部分复用意味着「这条缺陷由用例 A 覆盖，用例 B 还没找到」——
但处置结论集合里**没有**"部分覆盖"这一档（只有 `derived`/`reused`/`unresolved`）。
硬塞进 `reused` 就是**假装复用了**（F6 禁止）；塞进 `unresolved` 并点名缺口，是"显式说不知道"。

**影响面**：F2.2；判据 AC-009②。

## D74　特征匹配的归一化口径与匹配规则（写死）

**背景**：F2 规则 2 要求「特征 = `command` 归一化 + `steps` 归一化后的指纹（归一化口径你定，
但要写进契约与 references）」。口径不写死 ⇒ 实现与验收各写一套 ⇒ 判据无法机械核。

**决策**：归一化 `norm(s)`（按顺序）：

1. Unicode **NFKC** 规范化；
2. 去首尾空白；
3. 连续空白（`\s+`）压缩成**单个空格**；
4. 剥掉**成对包裹**的引号（`"…"` / `'…'` / `“…”` / `‘…’`）；
5. 去**末尾**标点（`。．.!！?？;；,，`）；
6. 再去首尾空白。

- **steps 指纹** = 各步 `norm(action)` 用 `\x01` 连接；
- **特征指纹** = `norm(command)` + `\0` + steps 指纹；
- **匹配规则**：某条已有用例与缺陷单的 **steps 指纹逐项相等**，**且**
  （两侧 **command 指纹相等** **或** 两侧 command **其一为空**）⇒ 命中。

**理由**：这四步变换都是**不改变语义**的（NFKC 统一全/半角、压缩空白、剥引号、去尾标点），
所以"命中"确实意味着同一件事；而"其一为空即放行"是为了让**没有 `reproduction` 字段的 v2 用例**
（上游 v2 用例集本来就没有这个字段）也能参与匹配。

**被否掉的替代方案**：

- ❌ 只比 `command` —— `command` 常缺失，等于匹配能力归零；
- ❌ 只比 `steps` 的**包含**关系 —— "以满减券下单"是"以满减券下单并支付"的子串，
  会把不同步骤的用例误判成同一个 bug 的复现。

**影响面**：F2.3；`references/derivation-rules.md` 必须原样写出这套口径；判据 AC-010。

## D75　判定顺序：`case_refs` 优先，信息充分性只是派生分支的前置

**背景**：F2 列出 1/2/3 三条规则并说「按下列顺序判定」，但规则 3（信息不足）的**触发时机**含糊：
一条缺陷既有 `case_refs`（命中）又缺 `reproduction` 时，按 1 判 `reused`，还是按 3 判 `unresolved`？

**决策**：判定顺序固定为

```
① case_refs 非空？ → 是：查用例集 → 全中 ⇒ reused；任一未中 ⇒ unresolved
                  → 否：② 信息充分？（F1.3）否 ⇒ unresolved
                                是：③ 特征匹配 → 命中 ⇒ reused；未命中 ⇒ derived
```

即：**信息充分性只在"要派生"之前检查**。`reused` 不需要 `reproduction`。

**理由**：`reused` 的语义是"这条缺陷已有用例在测"，与缺陷单里有没有写复现步骤无关。
为一个**已经能复用**的缺陷判 `unresolved`，等于因为缺陷单写得糙就丢掉一条现成的覆盖。

**影响面**：F2.1；判据 AC-009 / AC-010 / AC-012。

## D76　输出文档的 `requirements[]` 只含缺陷条目

**背景**：F3 要求「`requirement_refs` 非空且**不悬空**（硬约束 10）→ 文档 `requirements[]` 里
**为每个缺陷建一条条目**（`id` 用 `R-1`、`R-2`… 按缺陷顺序）」。
但 `reused` 的用例**沿用原用例的 `requirement_refs`**（指向**原套件**的 `R-<n>`），
而本轮文档的 `requirements[]` 里也有 `R-1`、`R-2`… —— **编号语义撞车**：
同一个 `R-1` 在两份文档里指两件不同的事。

**决策**：

1. 输出文档的 `requirements[]` **只含缺陷条目**（每个缺陷一条，`R-1`…`R-<n>` 按缺陷在输入中的顺序，
   `source_ref` = `defects.json#/defects/<下标>`）；
2. **复现用例的 `requirement_refs` 一律指向"它所复现的那个缺陷"的 `R-<n>`** ——
   `reused` 与 `derived` **同**；
3. ⇒ `requirement_refs` **非空且不悬空**（硬约束 10 得证）。

**理由**：本轮文档的主题是**缺陷**，不是原套件的需求。复用的原用例自己的需求条目归属原套件，
搬进本轮只会造成编号语义撞车（比悬空更隐蔽 —— 它**不报错**，只是悄悄指错了地方）。

**被否掉的替代方案**：

- ❌ 把原套件的 `requirements[]` 一并复制进来 —— 两套 `R-<n>` 必然撞号；
- ❌ 复用的用例保留原 `requirement_refs` —— 悬空（AC-016 判红）或语义错指。

**影响面**：F3.4 / F4.1；判据 AC-016 / AC-020。

## D77　复现用例的 `status` 一律 `active`

**背景**：F3 说「`status`：`active`（**新派生的**复现用例一律 active）」，没说复用的用例怎么办。
若把原用例的 `status` 原样搬过来，原用例若是 `deprecated`（需求已删），
本轮就产出了一条"已废弃"的复现用例 —— 它不会被执行，等于这条缺陷**没被复现**。

**决策**：

1. 输出里**每条**复现用例的 `status` 一律为 `active`；
2. 若被复用的原用例 `status == "deprecated"` ⇒ 该缺陷**改判 `unresolved`**，
   `reason` 说明"原用例已废弃，无法作为复现用例复用"。

**理由**：R3 的目的是"让已知缺陷有一条可重跑的用例"。把一条已废弃的用例拉过来当复现用例，
是**名义上有覆盖、实际上跑不了**。宁可说不知道（`unresolved`），也不产出假覆盖。

**影响面**：F3.2；判据 AC-014（处置结论互斥且完备）/ AC-016。

## D78　F7「输出目录已存在且非空」的判定口径

**背景**：F7 写「输出目录若已存在且非空 → 报错退出（不得覆盖别人的东西）；输出目录不存在 → 创建」。
但 F4.3 要求产物落 **`test-assets/cycles/<R3 轮次>/`** —— 那个目录**本来就有 `cycle.json`**，
按字面读「非空就报错」，本 REQ 的默认用法会**立刻报错**。

**决策**：判定对象是**产物文件**与**目录内容**，不是"目录非空"这一条：

| 情形 | 判定 |
|---|---|
| `<out-dir>/defect-cases.json` **已存在** | **报错退出**（不得覆盖别人的东西） |
| `<out-dir>` 不存在 | **创建** |
| `<out-dir>` 存在，且含**除 `cycle.json` 之外**的任何文件 | **报错退出** |
| `<out-dir>` 存在且只含 `cycle.json`（`--out-dir` 省略、默认 = `--cycle-dir` 时） | **允许** |

**理由**：这条纪律要防的是"把产物写进一个不相干的目录 / 覆盖掉别人的产物"。
轮次目录里那个 `cycle.json` 是**本轮自己的**既有文件，不是"别人的东西"。

**影响面**：F4.4 / F7；判据 AC-026④。

## D79　`cycle.json` 的 `trigger.ref` 必须 ∈ 输入缺陷 id 集合；工具只读不改写

**背景**：F5 要求 R3 轮次 `cycle.json` 的 `trigger` 是 `{"type":"defect","ref":"<BUG-id>"}`，
但没说 `ref` 与缺陷单怎么对齐（缺陷单可能一次含多条缺陷）。

**决策**：

1. `trigger.type` 必须是 `"defect"`；`trigger.ref` 必须 ∈ **输入缺陷 id 集合** ——
   否则轮次与缺陷单对不上，属**输入非法** → 报错退出（退出码 1）+ stderr 点名；
2. 工具**只读** `cycle.json`，**不得改写**它（逐字节未变）；
3. 轮次状态推进**不归本 REQ**（`cycle-state.mjs` 已支持 `--round R3 --round-type defect-verify`）。

**理由**：`trigger.ref` 若指向一个不存在的缺陷，轮次就"触发在空气上" ——
而轮次契约是 R3 的入口，不校验等于没有。

**影响面**：F5；判据 AC-027。

## D80　`defects[]` 条目字段集严格照 F4 规格

**背景**：复用的缺陷其 `expected_failure`（失败现象）在输出里无处安放：
复用的用例沿用**原用例**的 `steps`（原用例的断言已经编码了失败条件），
派生的用例则把 `expected_failure` 写进了 `steps[].expected` 与 `data`。

**决策**：`defects[]` 条目的字段集**封闭**，严格 = `id` / `title` / `severity` / `status` /
`disposition` + 条件字段 `reason` / `reused_case_refs` / `derived_case_id` / `source_cycle_id`。
**不额外加字段**（如 `expected_failure`）。

**理由**：

1. F4 已经把这一段的字段列表**写死**了 —— 实现方擅自加字段会让「产物形状」失去唯一性；
2. 信息并没有丢：复用的缺陷，失败条件由**原用例的断言**承载；
   派生的缺陷，失败条件在 `steps[].expected` 与 `data.expected_failure` 里。

**影响面**：F4.2；判据 AC-014④。

## D81　扩展编号段 `TC-101`~`TC-999`；用尽 ⇒ 改判 `unresolved`

**背景**：F3 说「扩展编号段 `TC-101` 起（`TC-001`~`TC-100` 留给原套件，避免与被引用用例撞号）」，
但没说段用尽了怎么办。上游硬约束 1：`id` 必须匹配 `^TC-\d{3}$` ⇒ **`TC-1001` 不合法**，
扩展段上限就是 `TC-999`（共 **899** 个号位）。

**决策**：扩展段 = `TC-101` ~ `TC-999`；扩展段用尽（全部被占用或已分配）⇒ 该缺陷
**改判 `unresolved`** 并给非空 `reason`。

**被否掉的替代方案**：❌ 允许 `TC-1001` 之类的四位数 id —— 与上游硬约束 1 直接冲突。

**影响面**：F3.1；判据 AC-013 / AC-015。

## D82　扩展段被占用 ⇒ 顺延到下一个空闲号

**背景**：扩展段里的号**可能已经被原套件占用**（比如原套件里就有一条 `TC-101`）。
固定从 `TC-101` 起编号会**撞号**。

**决策**：从 `TC-101` 起**向上扫描**，取第一个**既不在输入用例集里、也未被本轮已分配**的号位。

**理由**：撞号会产生**两个同 id 的用例** —— 一条原用例、一条复现用例，
执行器按 id 索引时哪条生效不可控，且证据目录也会互相覆盖。

**影响面**：F3.1；判据 AC-013（夹具刻意占用 `TC-101`，真值 `TC-102`）。

## D83　幂等口径：除 `meta.generated_at` 外逐字相同

**背景**：F6 说「同一输入两次运行，产物除 `generated_at` 外逐字相同」，
但产物里有两个可能带时间的地方：`meta.generated_at` 与（若实现想加）用例级时间戳。

**决策**：**唯一**允许变动的字段是 `meta.generated_at`。产物里**不得**出现其它随时间变化的字段。

**理由**：`meta.generated_at` 是"这份产物什么时候生成的"，其余任何字段都应是"关于缺陷与用例的事实"。
事实不该随时间变。

**影响面**：F6；判据 AC-024。

## D84　验收门的失败键口径与检出口径

**背景**：REQ-010 的教训 —— 门若用**对称差**或**全量 AC 编号**当基线失败键，
变异检测会退化成**橡皮章**（任何变异都被报成"已检出"，或任何变异都检不出），而门仍然 exit 0。

**决策**（REQ-007 的门必须照此写）：

1. **基线失败键只取 `^FAIL` 行**的 AC 编号 —— `PASS` / `UNDEC` 行里也有 AC 编号，
   混进来会让基线键集合变成**全集**，此后"新增失败键"要么恒空、要么恒等于全集；
2. **检出口径 = 新增失败键** = 变异运行的失败键 **减去** 基线失败键（整行精确排除）。
   **不用对称差** —— 对称差把"基线红、变异后绿"也算成变化，那是噪声；
3. **崩溃造成的判红是假检出**，不计入检出率（须自证：结构合法 + 脚本能正常跑完）；
4. 判据正文与门的理解有出入时，**以 `acceptance.md` 正文为准**，分歧写进脚本注释。

**影响面**：验收门 `verify-acceptance.sh`；验收纪律 §0 第 4/5 条。

## D85　负控 M0 必须无害，且其失败信号必须接进退出条件

**背景**：负控 M0 是"打不到任何判据的无害篡改"，它检验的是**探测器本身**。
若 M0 被报成"已检出"，说明探测器恒真 ⇒ 门失效。但若门**只打印**这件事却不因此退出非 0，
这个信号就等于没有 —— 门仍然 exit 0，验收结论照样被采信。

**决策**：

1. M0 必须是**无害**的改动（按 F4.1，`meta` 的字段集开放 ⇒ 往 `meta` 里加一个说明字段是安全的）；
2. M0 的失败信号**必须接进退出条件**：M0 被检出 ⇒ 门**非 0 退出**，
   并明确打印「门侧缺陷：探测器疑似恒真，本门结论不可采信」。

**影响面**：验收门的退出条件；D65 自测清单第 4 项。

## D86　门在无实现的真包上必须优雅降级

**背景**：本门在 Dev 实现**之前**就要写好并自测（D65）。被验包可能**完全没有**
`skills/defect-verify/`。

**决策**：门在缺少实现时：

- **不崩溃**（脚本自身不因缺文件而异常退出）；
- 相关判据如实报 **FAIL**（结构类）或**不可判定**（行为类：没有产物可判）；
- 变异体套件报**不可判定**并说明「**实现缺失**（不是门侧问题）」；
- 退出码**非 0**（不可判定 ≠ 通过）。

**理由**：一个"在没实现时也 exit 0"的门比没有门更危险 —— 它会让人以为验收过了。

**影响面**：验收门；D65 自测清单第 1 项。

## D94　`unresolved` 不是失败

## D97　同一用例被多个缺陷复用时的处置

**决策**：

1. **同一缺陷的 `case_refs` 内出现重复 id** → **先去重**再判（去重后按 D73 的「全部找到 ⇒ `reused`；
   任一找不到 ⇒ `unresolved`」判定）。
2. **多个缺陷引用同一条已有用例** → 产物里该用例**只出现一次**：
   - 该用例的 `defect_refs` 含**全部**引用它的缺陷 id（数组，长度可能 > 1）；
   - 该用例的 `tags` 含 `defect-verify` 与**全部**这些缺陷 id；
   - 该用例的 `requirement_refs` 含**全部**相关缺陷的 `R-<n>`（仍**不悬空**）；
   - 每条缺陷**各自**的 `disposition` 仍独立为 `reused`，各自在 `reused_case_refs` 里记下这条用例。
3. 派生（`derived`）的用例**只属于一条缺陷**（`defect_refs` 恰好 1 个元素）—— 派生是"为这条缺陷新造一条"。

**理由**：

- 若按"每条缺陷各产一条用例"处理，同一条已有用例会被复制成 N 条**同 id** 的用例 ——
  撞 `validate-cases.mjs` 的「用例 ID 重复」**硬拦** ⇒ 产物**不可执行**；
  门 AC-015 的「`id` 在产物内唯一」也会判红。实现方若拿不到这条裁定，只能靠猜，
  猜错就白跑一轮。
- 反过来，若把后一条缺陷改判 `unresolved`（理由写"该用例已被占用"），等于宣称
  「这条缺陷没法复现」—— 而它**本来就能复现**（用的就是那条已有用例）。
  这是**假的"不知道"**，违背 F6 的诚实性红线。
- **共享**才贴近真实语义：**一条用例可以复现多个缺陷**（同一根因的多个症状）。
  与 D73「不得部分复用」也不冲突：D73 说的是"复用要完整"，共享说的是"一条用例被完整地复用两次"。

**影响面**：F2.2（`case_refs` 去重）、F3.2（`defect_refs` / `tags` / `requirement_refs` 的取值）；
AC-009 与 AC-015 的判据正文；实现侧追溯范围随之为 **D72~D97**。
