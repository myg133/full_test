## 1. 岔路裁定（G1~G12）

### D185 ⭐ skill 归属（G1）

**裁定**：**仍在 `skills/load-profile/` 内**，加**第二个入口**（与 REQ-009 / REQ-012 同款延续）；**不新增**第 9 个 skill 目录。

**依据**：用户拍板；REQ-012 `PROBE-FACTS.md` B4（REQ-002.9 = `load-profile` skill「负载模型 + runner 适配」，B 阶段是该 skill 的第三半）。
**代价**：负载级产物与用例级 `test-execute` 形态不同 ⇒ **靠产物落点与判定口径区分**（D186 / D191），不靠 skill 目录区分。

### D186 负载级产物落点（G2）

**裁定**：
- 判定产物：`<out-dir>/test-assets/load/results/<套件名>.json`（**每套件一个**）
- 证据目录：`<out-dir>/test-assets/load/evidence/<套件名>/`（每条 invocation 一个子目录）

**依据**：REQ-012 勘察 H1（输入面已存在，输出面必须新造）；D6（`report.json` 顶层封闭 ⇒ 装不下 ⇒ 必须独立）。
**约束**：`results/` 与 `evidence/` 与 REQ-009 的 `report.json` / `scenarios/` / `suites/` / REQ-012 的 `plans/` **并列**、**互不覆盖**；
**计划文件绝不能叫 `suite.json`**（REQ-012 勘察 ⑦ 的同款红线）。

### D187 桩服务归属（G3）

**裁定**：桩服务是 **`load-profile` skill 的组成部分**，进交付包（`skills/load-profile/` 下），**随包分发**。

**依据**：H6（桩必须自带计数与延迟注入能力，否则「压了」不可证）；D8（工具不可用必须明确报错 ⇒ 桩不能靠人手工起）。
**约束**：桩**只监听回环地址**；桩**不含任何真实业务逻辑**；桩的配置面**封闭**（见 D193）。

### D188 阈值来源（G4）

**裁定**：阈值**直接吃 REQ-012 计划里逐字携带的 `thresholds`**（其上游是 REQ-009 模型的 `thresholds`）；
本 REQ **不引入第二份阈值配置**，也**不改**阈值键白名单（封闭 6 键，REQ-009 `profile-rules.md`）。

**依据**：F6（H1 输入面已存在）；REQ-012 `runner-adapters.md` §3.2（`thresholds` / `thresholds_source` 仅模型 `provided` 时携带）。
**约束**：模型 `thresholds_status == "not_provided"` ⇒ **无 `thresholds` 键** ⇒ 本 REQ **不产阈值判定**（只产执行事实），**不得**编造阈值。

### D189 `max_concurrency` 的处置（G5）

**裁定**：**判「不可判定」**，并在产物里**点名该键无对应观测量**。

**依据**：E 组（`Result` 里与并发相关的只有**配置值** `concurrency` 与**客户端数** `clients`，**都不是「实际达到的服务端并发」**）；
C7（桩的服务端并行处理能力不可从客户端侧推断）⇒ **换工具也未必解决**。
**红线**：**不得**拿 `concurrency`（打算并发多少）或 `clients`（客户端数）**冒充**「实际并发」去判达标 —— 那是凭空判达标。

### D190 判定粒度（G6）

**裁定**：**两者都要**：
1. **按 invocation 判**：每条 invocation 一个判定结果（阈值 vs 该次观测）；
2. **按 suite 汇总判**：整个套件一个汇总判定。

**依据**：D1（每 step 一条 invocation，**不许合并**——合并 = 丢梯度 = 失真）⇒ 只按 suite 判会把「哪一段崩了」抹平。
**约束**：汇总判定**不得**掩盖任何一条 invocation 的失败（存在任一 invocation 失败 ⇒ 套件汇总**不得**判「达标」）。

### D191 与 `test-execute` 的边界（G7）

**裁定**：**完全分家**。本 REQ **不写** `cases.json`、**不改** `test-execute` 的任何文件、**不碰** `results.json` / `meta.json` /
**不与** `test-execute` 的 `verdict.mjs` 混用、**不把**负载级结论塞进 `test-report` 的 `report.json`。

**依据**：D6（`report.json` 顶层封闭 8 键，`cases` / `regression` 段键集封闭，顶层只允许 `schema_version` 一个数字型叶子字段 ⇒ 装不下）；
REQ-012 勘察 E5/E6/E7（用例级证据链与负载级结构性不兼容）。
**后续**：若要让人在报告里看到负载结论，属 **REQ-010 的扩展**，**不在本 REQ**。

### D192 ⭐ 执行方式（G8）

**裁定**：**两者都支持**：
- **默认 `api`**：执行器 import `loadtest` 包，拿结构化 `Result`；
- **cli`**：由**执行器入口的命令行参数显式声明**（`--mode cli`）⇒ 逐字 spawn 计划里的 `argv`，**解析 stdout**。

**依据**：用户拍板；B1（CLI 无 JSON 输出）/ B2（包提供 API）/ B3（API 与 CLI 选项名不同）/ B4（API 天然等价 `--cores 1`）/
B5+B7（**不设 `statusCallback` ⇒ HTTP 错误码全塌成 `-1`，且 CLI 根本无法设置它** ⇒ 错误码分类能力是 API 独有）。
**约束**：
1. **`cli` 模式的声明位置只能是执行器入口的命令行参数** —— **不得**改 REQ-012 计划的字段集（顶层封闭 4 键），
   **不得**扩 REQ-012 的 `args` 白名单（封闭且「未知键拒绝」）；⇒ 满足用户「**计划显式声明时才走 CLI**」的意图，
   同时**不越界改上游契约**；
2. `cli` 模式**必须**如实标注**能力降级**（错误码只有 `-1` 桶 ⇒ 按状态码分类不可用；stdout 文本解析 ⇒ 可能解析失败）；
3. 两种模式的产物**必须**标注 `execution_mode`（`api_equivalent` / `cli_verbatim`），见 D200 / D201。

### D193 ⭐ 桩行为配置来源（G9）

**裁定**：桩行为**不进契约**（不改模型字段、不扩 `args` 白名单、不新增配置文件）；**执行器内建默认**
（0 延迟注入、0 错误注入、恒 200 响应），并提供**可选的执行器命令行参数**作为**唯一**注入口
（例：`--stub-delay-ms <N>` / `--stub-error-rate <0~1>`；**不给就是默认**）。

**依据**：用户拍板；D4（模型里没有任何位置能表达桩行为）/ F1（这是新发现的缺口）。
**后果与护栏**：
1. 产物**必须**记录**实际生效的**桩行为值（注入延迟、注入错误率、响应码）⇒ 读者能知道「这次压的是什么」；
2. **默认桩下，延迟类与错误率类阈值判「不可判定」**（见 D199）；
3. 桩行为**不进契约** ⇒ 本 REQ **不判**「桩行为是否完备」这类判据；
4. ⚠️ **本条是取舍不是最优解** —— 已登记遗留项（登记表）：想要「有代表性的延迟判定」时，
   必须靠执行器命令行参数注入，**契约层面无位置可放**。

### D194 URL 的 origin 替换规则（G10）

**裁定**：执行时**只替换 URL 的 origin**（协议 + 主机 + 端口）为**本地桩地址**；**path 与 query 逐字保留**。
（与 D201 的关系：「逐字 spawn」指的是**命令行形态**逐字，URL 的 origin 按本条换 ⇒ 二者**不冲突**。）

**依据**：D2（计划里的 URL 来自环境文件的 `base_url` ⇒ 指向真实服务地址）；A1（只打本地桩，绝不打真实服务）。
**约束**：
1. 替换后**必须**校验 URL 的 host 是**回环地址**（`127.0.0.0/8` 或 `::1`）⇒ **不通过 ⇒ rc=1 + 点名**（拒绝打非回环地址）；
2. 替换**不得**改动 path / query（否则压的就不是计划里那条链路了）；
3. 产物**必须**记录**替换前后的 URL**（替换前只记录 origin，**不得**把真实服务的完整 URL 当成敏感信息原样外泄？——
   本 REQ 判定：origin 逐字记录即可，path 逐字记录，**不做**脱敏（本地桩场景无凭证））。

### D195 「不可判定」的判定集合（G11）

**裁定**：`max_concurrency`（D189）· `python` runner（D203）· 默认桩下的延迟类与错误率类阈值（D199）·
`totalRequests == 0`（无任何请求完成）· `python` runner 的任何阈值 —— **一律判「不可判定」**，
**必须**点名「哪个键 / 哪条 invocation」不可判定及原因，**不得**判「达标」也**不得**判「不达标」。

**依据**：诚实性红线（不许凭空判达标）；REQ-012 契约教训（AC-021 ⑤⑦⑧ 互斥情形必须显式，不可含糊）。

### D196 桩实例与生命周期（G12）

**裁定**：
1. **每套件一个独立桩实例**，**端口 0**（随机分配）⇒ 同机多套件并行天然隔离；
2. 桩由**执行器托管**：起（等就绪）⇒ 跑 ⇒ 停（**收尾必停**，含异常路径）；
3. **收尾必须保证进程能退出**（keep-alive 的空闲连接会拖住 `close()`）⇒ 停桩时**连同残留连接一起断开**。

**依据**：C7（两套独立桩并发 ⇒ 计数零交叉）/ C8（手工起桩 ⇒ 桩残留）/ D9（F6）/
test-execute `executors/mock.mjs` 的 `stop()` 同款处置（`closeAllConnections()` + `close()`）。

### D197 判定不得依赖进程退出码

**裁定**：**判定链不得以压测进程的退出码为唯一依据**；退出码只区分「执行器自身出错」与「跑完了」。

**依据**：C5（桩中途被 `SIGKILL` ⇒ loadtest **不抛错、rc 仍是 0**，只是错误率飙到 62%）+
C4（全部失败时 `effectiveRps` 依然 5752）⇒ 靠退出码判 = **假绿**。

### D198 观测口径（客户端侧为主，桩侧为辅）

**裁定**：
1. **主观测量取客户端侧**（`loadtest` 的 `Result`）：延迟分位、吞吐、错误数 —— 它是「客户端体验」；
2. **桩侧观测**（请求计数、桩处理耗时分布）作为**辅助证据**落进产物，**不参与阈值判定**；
3. **两侧请求数不做等式判定** —— 实测客户端侧比桩侧**少约等于并发数**（在途请求：桩已收、客户端已被取消）。

**依据**：C1（14376 vs 14386，差 10 = 并发 10）/ C2 / C3（两侧延迟语义不同：客户端 RTT vs 服务端处理耗时）。

### D199 默认桩下延迟类与错误率类阈值判「不可判定」

**裁定**：桩行为为**默认**（未注入延迟、未注入错误）时，`p50/p95/p99_latency_ms` 与 `error_rate`
**判「不可判定」**并**注明原因**（「本次桩未注入延迟与错误，观测值只反映桩自身开销」）；
`throughput_rps` **仍可判**（客户端与桩之间的真实吞吐）。

**依据**：D193 的后果 + 诚实性红线（**把「0 延迟」判成「延迟达标」= 凭空判达标**）。
**注**：桩行为**由命令行参数注入**时（D193）⇒ 该两类阈值**恢复可判**。

### D200 API 模式 = 等价执行，必须标注

**裁定**：`api` 模式下**执行的不是 argv 里那条命令**，而是 argv 的**语义等价物**（B2/B3/B4）⇒
产物**必须**标注 `execution_mode = "api_equivalent"`，且**必须**记录**反解出来的实际执行参数**
（`maxSeconds` / `concurrency` / `requestsPerSecond` / `agentKeepAlive` / `timeout` / `url`）。

**依据**：F3（不标注 ⇒ 产物里的 `argv` 与真实执行的东西不一致 ⇒ **不可证伪** ⇒ 诚实性问题）。
**约束**：反解**只接受 REQ-012 规范形态**的 argv（D1）；遇到**规范外**的 argv ⇒ **rc=1 + 点名**（不得「尽力而为」地猜参数）。

### D201 CLI 模式 = 逐字执行 argv，stdout 解析，能力降级必须标注

**裁定**：`cli` 模式**逐字** spawn 计划里的 `argv` —— 指的是**命令行形态逐字不变**
（可执行名、参数名、参数顺序、参数个数**一个不改**）；**URL 的 origin 按 D194 换成桩地址**
（path 与 query 逐字保留）—— ⚠️ **桩端口是随机分配的**，计划里的 `8080` **不可能**是桩端口
⇒ 「逐字」与「换 origin」**不是两件冲突的事**，而是「命令行形态逐字 + URL 的 origin 按 D194 换」。
stdout **按已知文本形态解析**；**解析不出来 ⇒ rc=1 + 点名**（**不得**编造数值）。

**依据**：B1（CLI 只有文本 stdout）/ T5 实测的 stdout 形态（`Completed requests` / `Total errors` / `Mean latency` /
`Effective rps` / `50% 90% 95% 99% 100%`）。
**能力降级标注（必须）**：`error_code_resolution = "unavailable"`（只有 `-1` 桶）· `percentile_source = "stdout_text"`。
**约束**：CLI 模式**不设** `statusCallback`（做不到）⇒ **按状态码分类在 cli 模式下不可用**（D192 约束 2）。

### D202 `.loadtestrc` 渗透防护

**裁定**：`api` 模式**必须**显式覆盖每个相关 API 选项（使 `.loadtestrc` 的值**不生效**），并**显式禁用** `proxy`
（`.loadtestrc` 能塞 `proxy` ⇒ 流量可能走代理 ⇒ 打到非桩地址）。

**依据**：B12（`processOptions()` 无条件 `loadConfig()`；`.loadtestrc` 能改 `concurrency` / `requestsPerSecond` /
`method` / `headers` / `timeout` / `proxy` …）⇒ 不防护 ⇒ **同一份计划在不同宿主目录下跑出不同结果** ⇒ 幂等性破。

### D203 `python` runner 一律判「不可判定」

**裁定**：`runner == "python"` 的场景**照常执行**（逐字 spawn 自陈命令），但其**阈值判定一律「不可判定」**
（并点名「输出形态无契约」）；**不得**解析其 stdout 猜数值。

**依据**：D5（REQ-012 只钉了命令形态，**没钉输出形态**）/ F5。
**注**：本 REQ **不新造** `python` runner 的输出契约（那属 REQ-012 的延续，需改上游契约 ⇒ 越界）。

### D204 产物顶层封闭

**裁定**：`results/<套件名>.json` 的**顶层字段集封闭**（由 `acceptance.md` 钉死）；**任何**未登记的顶层键 ⇒ 判红。

**依据**：REQ-009 / REQ-010 / REQ-012 的同款纪律（顶层封闭 ⇒ 可机械核）。
**红线**：**不得**出现 REQ-012 §7 的那批「执行痕迹键」被**误禁**（那是「计划阶段」的红线；本 REQ **就是**执行阶段，
产物**必然**含执行痕迹）⇒ 计划阶段的禁键表**不适用于**本 REQ 的结果产物，但**仍适用于** `plans/`。

### D205 诚实性红线（产物级）

**裁定**：产物 / 结论**不得**出现「生产环境容量达标」「本服务可承载 N 并发」「压测通过（生产）」这类表述；
**必须**出现「**在本地桩上**」的限定。判定结论的措辞**必须**限定在「本次、本地桩、该负载模型」范围内。

**依据**：A2 / H7；REQ-009 / REQ-012 同款诚实性纪律。

### D206 工具可用性前置检查

**裁定**：执行前**必须**确认 `loadtest` **可用**（模块可解析 / CLI 可执行）；
**不可用 ⇒ rc=1 + 明确报错（点名缺什么、怎么装）**，**不得**「假装压过了」、**不得**产出「达标」结论。

**依据**：D8（本机实测 `which loadtest` 为空 ⇒ 工具**确实**可能不在）/ REQ-003 `qa-toolchain` 的 `qa doctor` 机制 /
D204（产物封闭 ⇒ 「没跑成」与「跑完不达标」必须能区分 ⇒ 失败**不产**判定产物，只报错）。

### D207 幂等性（**不承诺数值幂等**）

**裁定**：同一输入两次跑 ⇒ **产物结构、键集、判定口径**必须一致；**数值与结论允许抖动**（压测本身有随机性）⇒
**不承诺**「两次产物逐字相同」；产物**必须**记录实际观测值与执行参数，**不得**做「跑到过关为止」的重试取中位。

**依据**：压测是**随机过程**（实测两次同样的 3s/10c：14376 vs 14386 请求、p99 6 vs 5）⇒ 「逐字幂等」是**不可满足的判据**（不许写不可满足的判据）。
**与 REQ-012 的区别**：REQ-012 是**纯函数式规划**（⇒ 可承诺逐字幂等）；本 REQ 是**执行**（⇒ 只能承诺结构幂等）。

### D208 证据链与指纹

**裁定**：每次执行**必须**留下**可核验的证据**：
- 每次 invocation 的**原始结果**（api 模式：结构化 `Result` 的**选定字段**快照；cli 模式：stdout 原文）落进 `evidence/<套件>/<step>/`；
- 桩侧观测快照落进 `evidence/<套件>/<step>/stub-observations.json`；
- 证据目录含 **`manifest.json`**，**逐个列出该目录下每个证据文件的 sha256**（可被第三方独立复算）；
- 结果产物顶层 **`results_sha256`** = 对结果文件自身内容算的 sha256（**排除** `generated_at` 与 `results_sha256` 两个字段）。

**依据**：REQ-003~REQ-010 的证据链纪律（可核验是硬要求）；D198（桩侧作为辅助证据落盘）。

### D209 桩侧观测产物

**裁定**：桩侧观测**必须**落成独立文件，且**聚合**存储（按 ms 桶的直方图 + 计数 + 合计 + 极值），**不得**存全量样本。

**依据**：C9（1.4 万次请求存全量 ⇒ 观测输出十万级字符 ⇒ 产物爆炸）。

### D210 退出码语义

**裁定**（与 REQ-012 一致的两档 + 本 REQ 特有的一档）：

| 情形 | 退出码 |
|---|---|
| 执行完成，判定产物已写出 | `0` |
| 输入非法 / 工具不可用 / URL 非回环 / 判定链自身出错 | `1` |
| 用法错误（参数缺失 / 未知参数 / 多余位置参数） | `2` |

**约束**：**「跑完但不达标」也是 `0`**（达标与否是**产物里的判定**，不是退出码）—— 与 D197 一致。
