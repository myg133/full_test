### 2.1 关键结论（**需求方亲自跑出来的**）

| # | 结论 |
|---|---|
| 1 | `loadtest` **CLI 无 JSON 输出**，但**包提供 API**（结构化 `Result`）⇒ **API 路径优于 CLI** |
| 2 | ⚠️ **不设 `statusCallback` ⇒ 所有 HTTP 错误码塌成 `-1`**；且 **CLI 根本无法设置它** ⇒ 错误码分类是 API 独有 |
| 3 | ⚠️ **客户端侧请求数比桩侧少约等于并发数**（在途请求）⇒ 两侧计数**不可等式判定** |
| 4 | ⚠️ **桩中途挂掉 ⇒ loadtest 仍 rc=0** ⇒ 判定**不得依赖退出码** |
| 5 | ⚠️ **全部失败时 `effectiveRps` 依然很高** ⇒ 吞吐必须与错误率**联合判** |
| 6 | 两套独立桩（端口 0）并发 ⇒ 计数**零交叉** ⇒ 隔离方案可行 |
| 7 | **桩会残留** ⇒ 生命周期必须由执行器托管 |
| 8 | **桩侧逐条存延迟 ⇒ 产物爆炸** ⇒ 观测必须**聚合** |
| 9 | ⚠️ **REQ-003 样例清单的 `verify.match` 大小写与真实输出不匹配**（`Loadtest version:` 大写 L）⇒ 按样例抄会让工具被误判不可用（**上游样例笔误**） |

### 4.2 独立语义复算器（T1 同款，需求方侧）

**位置**：`~/.local/share/agent-runtime-data/tmp/req013/t1/recompute.py`（**过程件**，零 import 被验包，只用标准库）。

**做什么**：对一次执行产出的 `results/<套件>.json` **独立重算**（不读被验包一行代码）：
结构封闭（R-001~R-012）· `results_sha256` 复算（R-020）· 产物与计划逐字对齐（R-030~R-033）·
URL origin/path 与 argv 反解一致性（R-040~R-043）· 阈值映射与判定三态复算（R-050~R-054）·
汇总判定复算（R-060~R-061）· 两侧计数/累计口径/顺序（R-070~R-072）·
诚实性扫描（R-080~R-083）· 证据清单 sha256 复算（R-090）。

**自测结果**：**19/19 个负控全部被复算器抓到**（`--selftest`）。
⚠️ **自测设计上的一个坑（已修）**：负控改坏产物后若**不重算 `results_sha256`**，
sha 不一致会**顺带**把负控「抓到」⇒ **掩盖了针对性检查项的灵敏度** ⇒ 现在负控默认重算 sha。

⭐ **复算器自测抓出契约自身的两处矛盾**（已修正并提交 `2f188c5`）：
① `execution` 段原文写「恰好 7 键」，但 `cli` 是**条件键**（仅 cli 模式有）⇒ 改为「6 必填 + 1 条件」；
② AC-024 禁词表里的单独 `capacity` 会**误伤契约自身的夹具**（`thresholds_source = "capacity-targets"`）⇒ 去掉。

⚠️ 已知耦合（如实登记）：「场景顺序颠倒」这一变异会**同时**触发 R-071（累计口径检查）⇒
R-071 与 R-033 在该变异上有耦合；结论仍正确（R-033 精确抓到顺序错），但 R-071 的独立灵敏度
