## 0. 背景与边界

### 0.1 缺口具体长什么样

REQ-009（压测能力域）交了「负载模型」：把**容量目标 / 负载画像 / 指标阈值**翻译成一份可审阅的负载模型，
落成 `test-assets/load/` 下的 `report.json` + 模型文档。

REQ-012（A 阶段）交了「runner 适配」：把负载模型翻译成**真实压测工具能消费的命令清单**，
落成 `test-assets/load/plans/<套件>.json`，每条 `invocations[]` 一条命令（`argv` 数组）。

⇒ **两半拼起来仍然不压测**：命令清单交出去了，**没人执行它**；执行了也**没人按阈值判定**。
本 REQ 补的就是这两件事。

```
  容量目标 ──REQ-009──▶ 负载模型(report.json) ──REQ-012──▶ 命令清单(plans/*.json)
                                                                     │
                                                        本 REQ ▼    │ 执行 + 判定
                                                          负载级产物 + 阈值判定结论
```

### 0.2 本 REQ **只打本地桩服务**

**需求方 2026-11-14 拍板**：B 阶段**只打本地桩服务，绝不打真实服务**。

由此产生三条硬约束：

1. **结论的适用范围** —— 本 REQ 产出的一切结论都只是「**在本地桩上**」的压测结论。
   产物 / 报告 / 正文里**不得出现**「生产环境容量达标」「本服务可承载 N 并发」这类表述
   （诚实性红线，与 REQ-009 同款）。
2. **桩服务必须可观测** —— 不然「压了」这件事**不可证**。桩必须自带**请求计数**与**延迟注入/分布**能力
   （否则观测量只能来自压测客户端一侧的计时，桩侧无法交叉验证）。
3. **桩服务不得是「假服务」** —— 一个恒返回 200、恒 0 延迟的桩会让**吞吐与延迟指标全是假的**，
   判定链再严谨也是在判**一个假世界**。桩必须能按注入的延迟/错误率真实地拖慢与出错。

### 0.3 交付边界（不许越界）

| 边界 | 内容 |
|------|------|
| **只打本地桩** | 目标地址**必须**指向回环地址 / 本地端口；**任何**指向非回环地址的目标**必须被拒绝** |
| **不改 `test-execute`** | B 阶段产物**不塞进** `results.json` / `meta.json`，**不与** `test-execute` 的 `verdict.mjs` 混用 |
| **不改 REQ-009 的既有文件** | 负载模型侧（`report.json` 的产出逻辑）只读不改 |
| **不改 REQ-012 的既有文件** | 计划侧（`plans/*.json` 的产出逻辑）只读不改；本 REQ **消费**它 |
| **不发真实流量** | 不连公网、不连内网真实服务、不碰任何非桩地址 |
| **不装工具** | 不在交付里捆绑压测工具的安装逻辑；工具由 `qa` 工装（REQ-003）负责 |

## 1. 目标

1. **执行**：消费 REQ-012 的 `plans/*.json`，把每条 `invocations[]` **真的跑起来**（spawn 真实进程、真的发请求），
   并把每一次执行的**原始结果**落成**负载级**产物。
2. **判定**：消费 REQ-009 的阈值，对每次执行 / 每个套件给出**阈值判定结论**，
   并对**无对应观测量**的阈值键**显式判「不可判定」**（不得凭空判达标）。
3. **可证伪**：每次执行留下**可核验的证据**（原始结果文件 + 桩侧观测 + 指纹），
   使「压了没有、压得对不对」**可被第三方独立复核**。
4. **诚实**：产物与结论**不得超出「本地桩上」这个范围**；**不可判定**必须显式呈现。

## 2. 待勘察（本 REQ 的第一件事）

以下 8 组**尚未勘察**，任何一条都不得在契约里被当作已知事实：

| 编号 | 勘察对象 | 要回答的问题 |
|------|----------|--------------|
| **B1** | 桩服务的形态与生命周期 | 进程内还是独立脚本？端口怎么分配？启停怎么管？并发安全吗？退出怎么保证？ |
| **B2** | loadtest 结果文件的实际形态 | 产物 schema 是什么？稳定吗？失败/崩溃时是什么形态？可解析吗？ |
| **B3** | 阈值键 → 观测量的映射 | 逐键对应哪个观测量？`max_concurrency`（H5）怎么办？映射表**能不能机械核**？ |
| **B4** | 负载级产物与证据目录 | 形状定成什么样？证据目录与 `test-execute` 的 `evidence/` 并列还是分家？ |
| **B5** | 失败 / 超时 / 残留处置 | 压测进程崩了怎么办？桩没起来怎么办？进程残留怎么回收？ |
| **B6** | 幂等与并发隔离 | 同机多套件并行怎么隔开？端口 / 工作目录 / 指标 / 桩实例怎么隔离？ |
| **B7** | 与 `test-report`（REQ-010）的衔接 | 负载级结论要不要进 `report.json` / `report.md`？还是独立成另一类产物？ |
| **B8** | 观测口径归属 | 请求计数 / 延迟分布由**压测客户端侧**采还是**桩侧**采？两者都采时以谁为准？不一致怎么判？ |

> **勘察方法约束**（沿用 REQ-012 的纪律）：结论必须**第一手实测**（跑真的桩 + 真的压测工具 + 读源码），
> **禁止**凭文档/记忆/推测下结论；每一组勘察结论都要归档到 `PROBE-FACTS.md`，并注明**怎么测的**。

## 4. 明确不做的事（**不许越界**）

1. **不打真实服务** —— 不打公网、不打内网真实服务、不打任何非桩地址。
2. **不做容量结论** —— 不产出「生产能扛多少」的结论，只产出「本地桩上如何」。
3. **不改 `test-execute`** —— 不动它的产物形状、不动它的 `verdict.mjs`、不把负载级结果塞进它的 `results.json`。
4. **不重做 A 阶段** —— 不改 REQ-012 的计划产出逻辑，只消费。
5. **不重做负载模型** —— 不改 REQ-009 的模型产出逻辑，只消费。
6. **不凭空判达标** —— 无对应观测量的阈值键判「**不可判定**」，不判「达标」。
7. **不造假桩** —— 桩必须能真实地产生延迟与错误，否则结论无意义。
