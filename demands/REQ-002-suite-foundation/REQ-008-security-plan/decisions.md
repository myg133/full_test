## D98　`security-plan` 的入口脚本与产物落位

**决策**：

1. 入口脚本固定为 **`skills/security-plan/scripts/make-security-plan.mjs`**；
   自检器为 **`skills/security-plan/scripts/check-security-plan.mjs`**（两个都必须可执行、首行 `#!/usr/bin/env node`）。
2. `--out-dir` 的语义是**目标项目根**（不是「产物目录」）。产物固定落在：

```
<out-dir>/test-assets/security/
├── threat-model.json
├── matrix.json
└── suites/SEC-<编号>-<短名>/{cases.json,suite.json}
```

3. 工具**只写** `<out-dir>/test-assets/security/`，该路径之外的任何位置一律**只读**。

**理由**：

- 上游目录契约规定 security 资产住在 `test-assets/security/`（`project-layout.md` §2.2 差异表）。
  若 `--out-dir` 直接指「产物目录」，实现者就得自己决定拼不拼 `test-assets/security/` ——
  拼错了产物就落在契约外，上游校验器根本扫不到（等于产物不存在）。
- 把 `--out-dir` 定义成**项目根**，则「只写 out-dir」这条红线有了一个**机械可核**的落点：
  产物根恒为 `<out-dir>/test-assets/security/`，AC-028 的 ③ 才能核。

**影响面**：F1.1 / F1.5 / F6；AC-001 / AC-022 / AC-023 / AC-028；`references/security-context-schema.md` 必须写明该语义。

## D99　安全上下文 JSON 的字段集

**决策**：上下文 JSON 的字段集定为：

| 字段 | 必需 | 备注 |
|---|---|---|
| `schema_version` | 可选 | 若存在必须为 `1` |
| `service.name` | **是** | `service` 对象必填 |
| `assets[]` | **是** | `id` / `name` / `sensitivity` |
| `trust_boundaries[]` | **是** | `id` / `name` / `controls` |
| `entry_points[]` | **是** | `id` / `name` / `kind` / `asset_refs` / `boundary_refs` |
| `roles[]` | **是** | `id` / `name` |
| `resources[]` | **是** | `id` / `name` / `asset_refs` |

`description` / `from` / `to` / `data_flows` 等为**可选**说明字段。

**理由**：

- 施工单 F1 要求上下文**至少**能表达「服务名 / 信任边界 / 资产（含敏感度） / 信任边界（含控制点） / 入口点（外部输入面）」，
  并把字段集交给 BA 定。上面 6 段正好覆盖这 5 项（`trust_boundaries` 同时承载「边界」与「控制点」）。
- `roles` / `resources` 也定为**必填**：F4 的权限矩阵是「角色 × 资源 × 动作」，角色与资源必须**有出处**。
  若它们是可选的，实现者在没拿到角色/资源时就只能**自己捏造**，矩阵就成了自说自话 —— 那正好踩中
  F8 的「不得凭空造」红线。必填把「捏造」变成「必须先补上下文」。
- `controls` 允许是**空数组**（= 这条边界上没有控制点 —— 这本身就是要写进威胁模型的事实），
  但**不允许缺字段**（缺字段与「没有控制点」是两回事）。

**影响面**：F1.2；AC-005 / AC-006 / AC-007 / AC-008；`references/security-context-schema.md`。

## D100　用法错（rc=2）与输入非法（rc=1）的分层

**决策**：

| 情形 | 退出码 |
|---|---|
| 缺 `--context` / 缺 `--out-dir` / 出现不认识的开关 | **2**（调用方式错误） |
| 参数给了但**内容非法**（缺字段 / 类型错 / 枚举越界 / id 重复 / id 格式错 / 引用悬空 / `--scan` 形态无法识别） | **1** |

两种情形都**不得产出任何产物**。

**理由**：

- 与上游口径一致：`validate-cases.mjs` 与 `run-suite.mjs` 都把「调用方式错误」定为 2、
  「读到的内容不对」定为 1。门判的是**内容非法 ⇒ rc=1**，所以必须把这两类分开，
  否则实现者把「缺参数」也报成 1，门反而判红。
- 「不留半份产物」判的是**输出目录的实况**（`threat-model.json` / `matrix.json` / `suites/` 都不许出现），
  不是一个「先建目录再报错」的实现能糊弄过去的。

**影响面**：F1.4 / F1.5；AC-005 ~ AC-008。

## D101　id 命名规范与唯一性口径

**决策**：

| 对象 | 形态 | 唯一性 |
|---|---|---|
| 资产 | `^AS-\d{1,3}$` | 上下文内唯一 |
| 信任边界 | `^TB-\d{1,3}$` | 上下文内唯一 |
| 入口点 | `^EP-\d{1,3}$` | 上下文内唯一 |
| 角色 | `^ROLE-\d{1,3}$` | 上下文内唯一 |
| 资源 | `^RES-\d{1,3}$` | 上下文内唯一 |
| 威胁 | `^TH-\d+$` | 产物内唯一 |
| 扫描发现 | `^SCAN-\d+$` | 产物内唯一 |
| 未决问题 | 非空字符串 | 产物内唯一 |
| 安全用例 | `^TC-\d{3}$` | **跨全部 security 套件全局唯一** |
| 套件目录 | `^SEC-\d{3}-[a-z0-9][a-z0-9-]*$` | — |

**理由**：

- 威胁/用例的 id 是**追溯链的锚**（`source_ref` 里带 `TH-n`、`tags` 里带 `TH-n`），
  形态不统一就没法机械抽取引用关系。
- 用例 id **必须**是 `^TC-\d{3}$`：`validate-cases.mjs` 的 `CASE_ID_PATTERN` 是**硬拦**（L87 / L318）。
  架构文档 §8 的威胁模型示例写的 `TC-SEC-001` 与它**直接冲突** ⇒ 以校验器为准。
- 套件目录名沿用上游 `REQ-<编号>-<短名>` 的族式，security 用 `SEC-<编号>-<短名>`（`project-layout.md` §2.2）。

**影响面**：F1.2 / F2.2 / F5.3 / F6；AC-007 / AC-010 / AC-018 / AC-022。

## D102　威胁条目字段集与枚举取值

**决策**：威胁条目字段集**封闭 12 个**（见 `demand.md` F2.2），枚举取值：

- `category` ∈ STRIDE 六类：`spoofing` / `tampering` / `repudiation` / `information_disclosure` / `denial_of_service` / `elevation_of_privilege`
- `owasp` ∈ `A01`~`A10`
- `severity` ∈ `critical` / `high` / `medium` / `low`
- `source` ∈ `model` / `scan` / `model+scan`

**理由**：

- `category` 用 **STRIDE 六类**而不是 OWASP：方法库 M2.1 就是「威胁建模（STRIDE）」，
  `methods.json` 的 `M2.1` 描述明确写着「逐类过 STRIDE（身份伪造/篡改/抵赖/信息泄露/拒绝服务/权限提升）」。
  两个维度（`category` = STRIDE、`owasp` = A01~A10）各管一件事，不重复。
- `severity` 用四级（`critical`/`high`/`medium`/`low`），与既有 skill 的 `severity` 口径一致。
- `source` 三态而不是布尔：一条威胁可能**既**来自建模**又**来自扫描发现，硬写成布尔会丢信息。

**影响面**：F2.2；AC-010。

## D103　OWASP 十类的「交代」口径：**不指定**哪一类必须不适用

**决策**：

- `owasp_coverage` 的键集**恰为** `A01`~`A10`；每一类的 `status` ∈ {`covered`, `not_applicable`}。
- `covered` ⇒ `threat_refs` 非空且被引用威胁的 `owasp` 等于该类。
- `not_applicable` ⇒ `reason` 非空 **且** `open_question_ref` 指向 `open_questions[]` 里一条 `category` 等于该类的条目。
- **契约不指定**「哪一类必须判不适用」。

**理由**：

- 施工单 F3 的第一句是「A01~A10 十类必须全部有威胁（每类 ≥1 条）」，第二句才给出「确实不适用 ⇒ 显式记 not_applicable + 非空理由 + 留一条 open_question」的出口。
  两句合起来的正确读法是：**默认每类都要有威胁；确实不适用的才显式声明**。
- 但「**确实**不适用」是**语义判断** —— 门没法机械核「实现选的这一类是不是真的不适用」。
  若门硬写死「A02 必须不适用」，就把实现的判断抄进了契约；换一个服务形态（真有加密环节的服务）
  这个判据就变成**假判据**。
- ⇒ 门只核**两件可机械核的事**：①**交代完整**（十类每类都有声明，不许静默跳过）；
  ②**声明与事实一致**（covered 有真实威胁支撑；not_applicable 没有该类威胁、有非空理由、留了未决问题）。
  这既保住了「不许静默跳过」，又不越界替实现做判断。
- 夹具（`acceptance.md` §0.1）刻意造了一个**没有任何密码学资产**的服务，
  让「`A02` 确实不适用」成为实现**读得出来**的结论；判定它适用或不适用的**权利**仍归实现。

**影响面**：F3.1 / F3.2；AC-011 / AC-012 / AC-027；`acceptance.md` §0.1 与 §0.6 的诚实声明。

## D104　四类实战补充的显式判定口径

**决策**：`supplements` 的键集**恰为** `{file_upload, ssrf, xxe, deserialization}`；
取值形状与 `owasp_coverage` 同构；`covered` 时被引用威胁的 `supplement_refs` **必须含该键**；
`not_applicable` 时 `reason` **非空**。

威胁条目因此多一个字段 `supplement_refs`（数组，可为空）。

**理由**：

- 施工单 F3：四类实战补充「**不强制**每个项目都有，但**必须逐类显式判定**」。
  「逐类显式判定」要有机械落点，就得有一个**固定键集**；键集固定 ⇒ 判据可核「四类都在，且都有交代」。
- `supplement_refs` 这个字段是为了让「声明 covered」**可核**：光看 `supplements.xxe.threat_refs` 非空，
  只能证明实现指了个威胁，证明不了那条威胁真的管 XXE。把关联写进威胁条目，双向才闭合。

**影响面**：F2.2 / F3.3；AC-010 / AC-013 / AC-027。

## D105　权限矩阵的形状与 `basis` 口径

**决策**：

- `matrix.json` 的 `roles` / `resources` 与上下文对应段**集合相等**；`entries` 非空；
  每个 `(role, resource)` 组合**至少**一条 `entries`。
- `entries[].basis` ∈ {`expected`, `gap`}：
  - `expected` ⇒ `threat_ref` **必须为 `null`**；
  - `gap` ⇒ `decision` **必须为 `allow``，`threat_ref` **非空**。

**理由**：

- 施工单 F4：「矩阵里的**允许缺口**（本应拒绝却允许）⇒ 必须能对应到一条威胁（越权类）」。
  「本应拒绝」这句话没法从矩阵自身推出来（矩阵只记录**现状**），所以引入 `basis` 把
  **现状**（`decision`）与**期望**（`basis`）分开记 —— 只有实现自己能说出「这条本应拒绝」。
- `basis` 只用两值（`expected` / `gap`）而不是三值（`expected` / `gap` / `unknown`）：
  多一个 `unknown` 就会变成「什么都能往里塞」的逃逸口（声明成 unknown 就不用对账了）。
- `expected ⇒ threat_ref 必须为 null`：让「被引用的威胁」**唯一地**表示「这条决策有问题」，
  否则同一对威胁/矩阵关系有两种写法，追溯就断了。

**影响面**：F4；AC-015。

## D106　「越权类威胁」的定义与**双向**对应

**决策**：

- **越权类威胁** = `category == "elevation_of_privilege"` 的威胁。
- 每条越权类威胁，**必须**被至少一条 `basis == "gap"` 的矩阵条目引用。
- 每条 `basis == "gap"` 的条目，其 `threat_ref` **必须**指向一条越权类威胁。

**理由**：

- 双向是防「假覆盖」的关键。只做单向（有 gap 的必须指向越权威胁）的话，
  实现可以**完全不造越权威胁**、也不造 gap —— 矩阵就只剩「一切正常」的记录，
  而项目里明明有越权缺口（夹具里 `ROLE-2` 能读 `RES-2` 却只校验登录）。
  反向那条（越权威胁必须落在矩阵上）保证「识别出了越权」和「矩阵里承认了它」是同一件事。
- 用 `category` 而不是 `owasp` 来定义「越权类」：`owasp` 的 A01~A10 是**分类标签**，
  同一类（A01 访问控制失效）下可以有 spoofing、tampering、elevation_of_privilege 多种；
  用 STRIDE 的 `elevation_of_privilege` 判定「越权」更直接，也与 F4 的措辞「越权类」对齐。

**影响面**：F4 / F2.2；AC-016。

## D107　用例 id 的分配规则

**决策**：

- 形如 `^TC-\d{3}$`；
- **跨全部 security 套件全局唯一**；
- **不得**与 `--cases` 输入集里已有的 id 冲突；
- **具体编号由实现分配，契约不指定**。

**理由**：

- 「全局唯一」而不是「文件内唯一」：安全套件可能被一批跑（`test-execute` 的证据链按 run 归集），
  同号用例跨套件重复会让执行侧分不清是哪条。REQ-007 的 D97 已经因为「多缺陷共享一条用例 ⇒ 同 id 重复」
  撞了上游硬拦，本 REQ 提前把口径定死。
- 「不与输入集冲突」：REQ-007 的 D82（扩展段顺延）是同一个教训的另一面 ——
  派生的号撞上输入集已占用的号，产物就与既有资产混淆了。
- **不指定具体编号**：编号怎么分配是实现自由，契约写死编号等于把实现抄进契约（假判据）。
  §0.6 的真值表因此只固定「形态 / 唯一 / 不冲突」三条。

**影响面**：F5.3；AC-018。

## D108　威胁 ↔ 用例的关联靠 `source_ref`，不靠 id 后缀

**决策**：

- `requirements[].source_ref` **恰为** `threat-model.json#/threats/<TH-id>`（固定写法）。
- `requirements[]` 与威胁**一一覆盖**：每条威胁至少一条 requirement，每条 requirement 指向真实威胁。
- 用例通过 `requirement_refs → requirements[].id → source_ref` 反推它覆盖哪条威胁；
  `cases[].tags` 里**冗余**写上 `security` 与威胁 id（便于按威胁分批跑）。

**理由**：

- 施工单 F5 已点明：「威胁↔用例的关联靠 `requirements[].source_ref`，不靠 id 后缀」。
  原因很直接：`TC-SEC-001` 这种带后缀的 id 与上游 `^TC-\d{3}$` **硬拦**冲突。
- `source_ref` 用**固定写法**（而不是「随便写个字符串」），
  门才能用正则从产物里把 `TH-n` 抽出来做集合比对 —— 这是 AC-019 能机械核的前提。

**影响面**：F5.4；AC-019 / AC-021。

## D109　产物 `cases.json` 的顶层字段集**封闭 7 个**（由门判，不是上游判）

**决策**：产物 `cases.json` 的顶层字段集**恰为** 7 个：
`schema_version` / `meta` / `requirements` / `open_questions` / `coverage_matrix` / `defects` / `cases`。

**理由（口径必须写准，不许写假话）**：

- 上游 `validate-cases.mjs` 在 **v2 严格模式**下用 `failOrWarn` 处理**缺失**的顶层字段
  ⇒ 严格模式下缺 `requirements` / `open_questions` / `coverage_matrix` 是 **FAIL**。
- 但上游**没有**「顶层未知字段」这道检查 —— `validate-cases.mjs` L142 那道「出现未知字段」
  **只针对 `steps[].expected` 断言对象的字段集**，不针对顶层。
  ⇒ 「顶层封闭 7 个」**必须由本 REQ 的门用独立复算器核**，
  判据正文里**不能**写成「上游校验器会拦」—— 那是假话。
- `defects` 在这 7 个里但上游不校验它：它是 REQ-007 引入的用例集顶层段，
  封闭集合按**已交付的 v2 形状**取 7 个（REQ-007 的产物 `defect-cases.json` 也是这 7 个）。
  安全用例集里 `defects` 固定为 `[]`（本 REQ 不产生缺陷）。

**影响面**：F5.2；AC-020；验收门的独立复算器（`judge.mjs`）。

## D110　套件怎么分组由实现决定

**决策**：契约只要求「**至少 1 个**套件目录，目录名匹配 `^SEC-\d{3}-[a-z0-9][a-z0-9-]*$`」，
**不规定**套件的数量、编号与短名。

**理由**：

- 威胁按什么维度分组（按资产？按 OWASP 类？按入口点？）是**实现的设计选择**，
  每种都合理。契约写死分组 = 把实现抄进契约。
- 门因此只核**可机械核**的部分：目录名合规、每个目录有 `cases.json` + `suite.json`、
  `suite` 与目录名一致、`suite.json` 字段集封闭、**跨全部套件聚合**后的用例覆盖与 id 唯一性。
  换句话说：**分组的自由度留给实现，聚合后的性质由门守**。

**影响面**：F6；AC-017 ~ AC-023；`acceptance.md` §0.6 第 22 行。

## D111　F6「可被消费」= **加载层**可解析（**不要求**执行器可跑）

**决策**：F6 的「可被消费」判据落在**加载层**，具体是四件事：

1. `loadSuite(<suite.json>)` 成功（不抛错）；
2. `loadCases(<cases_file 解析结果>)` 成功（不抛错）；
3. `selectCases(cases, suite.json.tags)` 能按 tags 选出用例；
4. 产物 `cases.json` 过 `validate-cases.mjs`（退出码 0）。

**明确不要求**：`run-suite.mjs --dry-run` 跑通、**更不要求**执行器能跑。

**理由**：

- `test-execute/executors/index.json` 的 `not_implemented` = `["ui", "load", "security"]`，
  其 note 原文写着「分别属后续 REQ」。
- `run-suite.mjs` 的**执行器查找（L222-235）在 dry-run 分支（L240）之前**
  ⇒ 对 `executor=security` 的套件，`--dry-run` 会**先抛错**「执行器 "security" 尚未实现」，
  **根本到不了 dry-run 分支**。
- ⇒ 把「`--dry-run` 跑通」写进判据 = 写进一条**永远不可满足**的判据 = 永远「不可判定」，
  是本项目要避免的**假判据**形态。安全用例的**执行**属后续 REQ。
- 「可被消费」在判据正文里必须**点出「加载层」**三个字，并在「类型」里标为**一致性**类，
  以免验收方把它读成「能跑通执行」。

## D113　依赖扫描的职责边界与 `--scan` 的三种输入形态

**决策**：

1. **`security-plan` 自己不跑扫描器**（零第三方依赖、不联网、保持纯函数化可测）。
   扫描由 agent 用已交付的 `qa-toolchain`（`bin/qa`）跑 bandit / npm audit 后，**把结果喂进来**。
2. `--scan` 接受**三种**合法形态：
   - **bandit 结果**（根对象且 `results` 是数组）⇒ `tool = "bandit"`；
   - **npm audit 结果**（根对象且 `vulnerabilities` 是对象）⇒ `tool = "npm-audit"`；
   - **扫描状态**（根对象且 `status` ∈ {`unavailable`, `failed`}）⇒ `reason` 必填非空、finding 数 0。
3. 三者都识别不出来 ⇒ **输入非法** ⇒ rc=1。

**理由**：

- 施工单 F7 已把职责边界定死：扫描由 agent 用 `qa-toolchain` 跑，工具链契约里 **bandit 已声明
  `required_by: ["REQ-002.8"]`**（kind=python，PyPI 可达）。
- 「工具装不上必须显式报 `failed` / `unavailable`，不得静默跳过」是工具链契约的铁律。
  但「装不上」这件事**发生在 `qa-toolchain` 侧**，不是 `security-plan` 能自己知道的 ——
  所以必须给 agent 一个**把「没扫成」这件事说出口的输入通道**，这就是第三种形态。
  没有它，agent 只能悄悄不传 `--scan`，而「不传」在下游看起来和「扫了但没问题」**一模一样** ——
  那正是 F7 要防的「静默跳过」。
- 三种形态而不是一种：bandit 与 npm audit 是**两种真实存在**的扫描器输出，形状不同；
  第三种承载「没扫成」。

**影响面**：F7.1 / F7.2；AC-008 / AC-014；`references/threat-model-format.md`。

## D114　`scan.status` 的四态与「未提供扫描 ⇒ 不得声称已做扫描」

**决策**：

- `scan.status` ∈ {`provided`, `not_provided`, `unavailable`, `failed`}，**永远存在**于产物里。
- `not_provided` ⇔ 没有传 `--scan`；`unavailable` / `failed` ⇔ 传了「扫描状态」形态；
  `provided` ⇔ 传了 bandit / npm audit 结果。
- `scan_findings` 的条数**等于**输入扫描结果的 finding 数（一条输入 finding ⇒ 一条 `scan_finding`）。
- 每条 `scan_finding` 的 `threat_refs` **非空**且指向真实威胁；
  被引用威胁的 `source` 必须含 `scan`、`scan_refs` 必须含该 finding 的 id。
- **未提供扫描时**：不得出现 `source` 含 `scan` 的威胁；不得声称「已做依赖扫描」。

**理由**：

- F7：「扫描没喂 / 工具不可达 ⇒ 产物里必须**显式**声明（不得静默跳过）；未提供扫描时，**不得**声称「已做依赖扫描」」。
  「显式声明」必须有落点 —— `scan.status` 就是那个落点。
- 「finding 数 == 输入 finding 数」是**唯一**能把「喂进来的扫描结果被完整消费了」变成可机械核的规则：
  少了就说明丢了几条发现，多了就说明凭空造了几条发现。

**影响面**：F7.3；AC-014；AC-027。

## D115　幂等口径、只写自己的目录、产物已存在即报错

**决策**：

## D116　验收门的**失败键口径**：只取 `^FAIL` 行；检出 = **新增失败键**

**决策**：

- **基线失败键** = 基线运行里**失败**的判据编号，**只取 `^FAIL` 行**。
- **新增失败键** = 变异运行的失败键 **减去** 基线失败键（整行精确排除）。
- **检出** = 目标判据出现在**新增**失败键里。
- **不用对称差**：对称差把「基线红、变异后绿」也算成变化，那是噪声不是检出。

**理由**：

- 这是本项目**连续两轮踩坑**的地方（REQ-010 的最致命一处缺陷、REQ-007 的 F-01）：
  `PASS` / `UNDEC` 的输出行里**也含 AC 编号**，混进基线键集合会让它变成**全集**，
  此后任何变异的「新增失败键」都恒为空或恒等于全集 ⇒ **整套检测沦为橡皮章，而门仍然 exit 0**。
- 「不用对称差」的理由同上：对称差把「基线红、变异后绿」算成变化。

**影响面**：验收门 `verify-acceptance.sh`；`manifest.json` 的 `mutations.detection_metric`。

## D122　门内「独立复算器」与「上游加载层检查」**分进程**

## D126　安全套件所指向的**环境不写 `driver`**（避免「误配对 ⇒ 假象」）

**决策**：对 `scope=security` 的套件，其 `environment` 指向的环境定义**应当不写 `driver` 字段**。
夹具（`acceptance.md` §0.4）的环境定义**必须**不写 `driver`。

**理由**：

- 上游 `resolveDriverName()`（`suite-loader.mjs` L240-258）的优先级是

- ⇒ 本条与 D111（判据只到加载层）**互相加强**：夹具不写 `driver`，
