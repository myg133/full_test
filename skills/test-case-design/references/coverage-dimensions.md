# 覆盖维度清单

用例的 `dimension` 字段取自下面 11 个取值。**以 `references/dimensions.json` 为准** —— 它是维度枚举的唯一来源，
本清单与它的一致性由脚本对照保证（不需要人工同步）：

```console
node scripts/check-methods.mjs --methods references/methods.json --dimensions references/dimensions.json \
  --dimensions-doc references/coverage-dimensions.md --check-dimensions-doc
```

清单与库不一致时该命令退出码非 0，并点名不一致的维度 id。

| 取值 | 中文名 | 关注的问题 |
|------|--------|------------|
| `functional` | 功能 | 主流程按需求正确执行，结果符合预期 |
| `boundary` | 边界 | 临界值、最小/最大、超限一点点、临界点两侧 |
| `exception` | 异常 | 非法输入、依赖失败、超时、中断、重试后的行为 |
| `permission` | 权限 | 角色差异、越权访问、数据可见范围 |
| `data` | 数据 | 字段精度、格式、枚举取值、空值、大数据量、跨字段一致性 |
| `concurrency` | 并发 | 并发写入、重复提交、竞态、幂等 |
| `performance` | 性能 | 响应时间、吞吐、容量上限、资源占用 |
| `compatibility` | 兼容 | 端/版本/浏览器/协议版本差异下的行为 |
| `security` | 安全 | 认证与会话、输入解析（注入）、凭据与密钥、敏感数据脱敏与传输加密、审计可追溯 |
| `stress` | 压力 | 接近与超出设计容量时的行为正确性：限流与拒绝、优雅降级、背压排队、超时不丢数据 |
| `observability` | 可观测性 | 关键路径日志、日志级别与内容正确、错误可诊断、关键指标与告警、链路追踪、敏感信息不入日志 |

## 逐维度检查清单

对每个可测试需求条目，逐条问"这一条适用吗"，不适用的在报告里写明理由。

### functional（功能）
- 需求描述的行为是否都走到了？每条动作的输出是否符合需求原文？
- 同一功能的多个路径（创建/查询/更新/删除）是否都有用例？
- 步骤与预期是否可判定：预期里要能看出"看到什么就算通过"。

### boundary（边界）
- 取值范围的两端与两端外一格：下界-1、下界、上界、上界+1。
- 空值与零值：空串、null、0、"0"、单个字符。
- 长度/数量/金额的边界：0、1、上限、上限+1。
- 边界点两侧各一条用例，因为两侧走的是不同代码分支。

### exception（异常）
- 输入不合法时系统给什么反馈（错误码/提示语/是否泄漏内部信息）。
- 依赖不可用、超时、返回脏数据时的降级行为。
- 操作中途失败后的状态：是否留下半成品数据，是否可重试。
- 异常路径下是否仍然保证数据一致。

### permission（权限）
- 每个角色对同一资源的允许与拒绝行为（正向 + 反向都要有用例）。
- 越权路径：改 URL 参数、换 token、直接调底层接口。
- 数据可见范围：本人/本部门/全量。

### data（数据）
- 字段类型、精度（小数位）、单位、字符集、是否允许空。
- 枚举字段的合法值与非法值。
- 跨字段一致性：结束时间晚于开始时间、金额合计等于明细之和。
- 大数据量与特殊字符：超长文本、emoji、引号、换行、SQL 关键字。

### concurrency（并发）
- 同一资源被两个请求同时修改的结果（最后写入生效还是被拒绝）。
- 重复提交/双击是否幂等。
- 计数型资源（余额、库存、配额）的并发扣减是否超卖。
- 并发下是否出现脏读、脏写。

### performance（性能）
- 需求中给出的时限/容量指标：P95 响应时间、单次处理量上限。
- 规模增长时的表现：数据量放大 10 倍后的耗时与内存。
- 长时间运行的稳定性（如果需求涉及）。

### compatibility（兼容）
- 端与版本差异：Web/移动端、不同浏览器、客户端版本、协议版本。
- 向后兼容：旧数据/旧客户端调用新版本时的行为。
- 降级路径：新特性关闭后是否回到稳定行为。

### security（安全）
- 认证与会话：登录态失效后的行为、令牌过期/伪造/重放、会话固定。
- 输入解析与注入：参数、请求头、文件、回调、消息里的注入型输入（SQL/命令/模板/路径）。
- 凭据与密钥：硬编码密钥、密钥轮换、凭据不落日志、不出现在错误信息里。
- 敏感数据：脱敏规则（手机号/身份证/卡号）、传输加密、导出与下载路径上的敏感数据。
- 审计留痕：关键动作是否留痕、日志内容是否足以追溯、审计日志本身不可被篡改。
- 与 `permission` 的分工：`permission` 管**授权**（角色差异/越权/可见范围），`security` 管**认证本身 + 输入安全 + 数据保密**。

### stress（压力）
- 接近容量上限时的行为：限流阈值触发点、拒绝时给的是明确错误还是超时/雪崩。
- 超出容量时的降级：哪些功能先降级、降级后结果是否仍然正确、有没有静默丢数据。
- 背压与排队：排队长度上限、超时后请求的去向、队列满时的拒绝策略。
- 洪峰下的正确性：并发扣减是否超卖、重试与幂等在洪峰下是否仍然成立、失败后可补偿。
- 与 `performance` 的分工：`performance` 管**指标是否达标**（响应时间/吞吐/容量上限），`stress` 管**压到极限时行为是否仍然正确**。

### observability（可观测性）
- 关键路径日志：每个关键动作是否都有一行可关联的日志，是否带得出可定位的标识（用户/订单/请求 id）。
- 日志级别与内容：级别是否正确（正常操作不报 ERROR、失败不报 INFO），内容是否包含足够上下文。
- 错误可诊断：失败时拿到的错误信息能否定位到原因，还是只有一个无信息的错误码或"系统异常"。
- 指标与告警：关键指标（成功率/耗时/队列长度/拒绝数）是否被采集，阈值越界是否告警。
- 链路追踪：跨服务调用是否能串起来，故障时能否定位到出问题的那一跳。
- 敏感信息不入日志：日志与追踪里不得出现密码、令牌、完整卡号等敏感字段。
- 与 `exception` 的分工：`exception` 管**失败时的行为**，`observability` 管**失败后能不能定位**。

## 优先级建议

优先级反映"这个缺陷漏掉的代价"，与维度正交：

- `P0`：阻断主流程、资损、数据安全/权限越权、结果错误且不可逆。典型维度：`permission`、`data`、`exception` 里的数据破坏类。
- `P1`：主流程可用但体验或效率明显受损，或次要功能完全不可用。
- `P2`：边缘场景、次要功能异常、有可接受的规避方式。
- `P3`：文案、样式、极低频路径。

用户给定优先级口径时以用户口径为准；未给定时按上表推断并在汇报中说明推断依据。

## 与设计方法的对应

维度回答"覆盖哪类风险"，设计方法回答"怎么系统性地产生这些用例"。常见组合：

| 场景 | 组合 |
|------|------|
| 长度/数量/金额有区间 | 等价类划分 + 边界值分析 → `boundary` |
| 多条件组合出结果 | 判定表 → `functional` |
| 对象有生命周期 | 状态迁移 → `functional` + `exception` |
| 参数多且互相独立 | 正交实验 → `functional` + `data` |
| 角色差异大 | 判定表（角色 × 资源） → `permission` |
| 依赖外部系统 | 场景法 + 故障注入 → `exception` |
| 有认证、注入、凭据或脱敏风险 | 威胁建模（STRIDE） → `security`；攻击面枚举 → `exception` + `security` |
| 有上传、回调、消息等外部输入入口 | 攻击面枚举 → `exception` + `security`；模糊测试 → `exception` |
| 有容量上限或洪峰场景 | 模糊测试 → `exception`；场景法（洪峰主流程） → `stress` |
| 失败后需要定位问题 | 状态迁移 → `exception`；场景法 → `observability` |
