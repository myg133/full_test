# 负载画像 / 阈值 / 对账规则

> 三组规则：**负载画像**怎么表达、**阈值**怎么才敢写、**对账**怎么算。

## 1. 负载画像（`profile`）

`profile` 封闭 2 个字段：`type`（画像类型）+ `steps`（梯度）。

### 画像类型（5 个）

| type | 含义 | 典型 steps 形态 |
|---|---|---|
| `constant` | 恒定压力 | 一档：`[{duration_s: 300, concurrency: 5}]` |
| `ramp-up` | 爬坡 | 递增：`[{60s,10},{120s,20}]` |
| `ramp-down` | 降压 | 递减 |
| `spike` | 尖峰 | 陡起的一档高并发 |
| `soak` | 浸泡 | 长时长、低并发、稳态 |

### 梯度（`steps[]`）

- 元素封闭 2：`duration_s`（**整数** ≥ 1）、`concurrency`（**整数** ≥ 1）；
- **步序本身就是语义**：先 10 并发爬到 20 与先 20 降到 10 是两种负载 ⇒ 产物里的
  `profile` 必须**逐字等于**输入（**含每一项的顺序**），实现里不做任何排序或归并；
- `concurrency` 是**并发数**，不是 RPS；RPS 之类的 runner 参数走 `args`（开放键值，原样透传）。

⚠️ 画像的枚举取值在**产物侧**也要核：输入层被绕过时，产物层仍要拦（`profile.type` 不在 5 值内 ⇒ 判红）。

## 2. 阈值：什么时候才敢写

### 2.1 成对规则（输入层）

`thresholds` 与 `thresholds_source` 必须**同时出现**或**同时不出现**：

| 情形 | 判定 | 理由 |
|---|---|---|
| 两个都没有 | 合法 | 该容量目标**没有指标来源** |
| 两个都有 | 合法 | 来源非空 + 阈值键 ∈ 白名单（6 个） |
| **只给一个** | **rc=1** | 「有阈值没来源」= 凭空拍；「有来源没阈值」= 自相矛盾 |

### 2.2 没有来源时的表达（产物层）

「没有指标来源就不拍阈值」用**键的有无**表达：

```
thresholds_status == "not_provided"
  ⇒ 产物里**没有** thresholds 键、**没有** thresholds_source 键
  ⇒ 且 open_questions 里**必须**有 ≥1 条 topic == "thresholds"
```

反之：

```
thresholds_status == "provided"
  ⇒ 两个键都在，且逐字等于输入
  ⇒ 且 open_questions 里**不得**有 topic == "thresholds" 的条目（没有缺口就不该留缺口）
```

⚠️ 「不写阈值」不是「阈值写 0」也不是「阈值留空对象」—— 是**键根本不存在**。

### 2.3 不得凭空加码

有来源时，产物的 `thresholds` **键集与值都逐字等于**输入：
输入只给了 `p95_latency_ms`，产物里**不许**冒出 `p99_latency_ms`（读者会以为 p99 也有依据），
也不许把 `800` 改成 `500`。

### 2.4 阈值键白名单（封闭 6）

| 键 | 值类型 | 含义 |
|---|---|---|
| `p50_latency_ms` | number ≥ 0 | 中位延迟 |
| `p95_latency_ms` | number ≥ 0 | P95 延迟 |
| `p99_latency_ms` | number ≥ 0 | P99 延迟 |
| `error_rate` | number ∈ [0, 1] | 错误率 |
| `throughput_rps` | number ≥ 0 | 吞吐 |
| `max_concurrency` | number ≥ 0 | 最大并发 |

键之外 ⇒ 输入非法（rc=1）；产物里出现表外键 ⇒ 判红。

## 3. 链路存在性对账（只对账，**不派生用例**）

对账只回答一个问题：**这条被压链路在功能用例集里到底有没有对应用例？**

### 3.1 归一化规则

1. 取输入用例集 `cases[].steps[].action`；
2. **归一化**：取「方法 + 空格 + 路径」，并**删掉路径中所有 `{...}` 占位符段**
   （`GET /api/v1/orders/{id}` → `GET /api/v1/orders`）；
3. 归一化结果**等于** workload 的 `target` 的用例 id，**按用例出现顺序去重** ⇒ `case_refs`；
4. `case_refs` **必须恰等**该集合（多一个、少一个都违规）。

归一化是必要的：功能用例的 action 天然带路径参数（`GET /api/v1/orders/{id}`），
而负载目标不带（`GET /api/v1/orders`）—— 不归一化就永远配不上，对账就成了摆设。

### 3.2 缺口必须显式

`case_refs` 为空 ⇒ 该场景的 `open_questions` **必须**有 ≥1 条 `topic == "coverage"`：

> 该被压链路在功能用例集里没有对应用例 ⇒ 这条负载**没有回归护栏** ⇒ 压测结论**没有对照**。
> 这个事实必须写在纸面上，而不是靠人记得。

### 3.3 明确不做

- **不派生**任何用例（派生用例是 REQ-006 用例设计侧的活）；
- **不写** `cases.json`（压测用例不是「步骤 → 预期」形态）；
- **不改**功能用例集（只读）。

## 4. 套件划分与覆盖完整性

| 规则 | 内容 |
|---|---|
| 分组 | 同一 `environment` 的容量目标归入**同一个**套件（多对一） |
| 编号 | 按 `environments[]` 的**出现顺序**分配 `001`、`002`、… |
| 短名 | 该套件**第一个**场景的 `name`（顺序 = 输入 workload 顺序） |
| 引用 | 套件级 `scenario.json` 用 `scenarios` **数组**引用本体，每项带 `path` / `id` / `name` |
| 防漂移 | 引用的 `id` / `name` 必须与本体**逐字相等** |
| 双向完整 | 每个容量目标**恰好**一个套件引用；每个套件**≥1** 个引用；每个场景**≥1** 次被引用；无孤儿套件 |

## 5. 诚实性红线（产物层的硬约束）

| # | 红线 | 机器可读的载体 |
|---|---|---|
| 1 | 没有指标来源 ⇒ 不写阈值 | `thresholds_status == "not_provided"` ⇒ 无 `thresholds` 键、无 `thresholds_source` 键 |
| 2 | 不得凭空拍阈值 | 有来源时 `thresholds` 逐字等于输入；输入没有的键不得出现在产物里 |
| 3 | 不得把「未压测」写成「已通过」 | 产物里**不得**出现任何压测结论字段（`status` / `result` / `verdict` / `executed` / `passed` / `outcome` / `conclusion`） |
| 4 | 缺口必须显式 | 无来源 ⇒ 必留 `topic=thresholds`；无对应用例 ⇒ 必留 `topic=coverage` |

## 6. 幂等与写入权

| 口径 | 落点 |
|---|---|
| 幂等 | 产物**不含**生成时间戳 ⇒ 同一输入两次跑（两个 `--out-dir`）出来的文件**逐字相同** |
| 只写自己的目录 | `<out-dir>` 下除 `test-assets/load/` 以外的一切**逐字未变**（环境 / 轮次 / `.gitignore` 一律只读） |
| 不改输入 | `--context` / `--cases` 指向的文件跑前跑后 sha256 **一致** |
| 产物已存在即报错 | `<out-dir>/test-assets/load/` 已存在（非空）⇒ **rc=1** 且**不覆盖**既有产物 |
